# 评估体系

> `CLAUDE.md` 拆出来的深潜正文（原「RAG 质量评估」「Agent 综合评估」「Agent 运行看板」三节）。
> 改检索 / 闸门 / 提示词，或动评估脚本之前，先把这里读完。

## RAG 质量评估（`scripts/eval_rag.py`）

**为什么要自己实现**：RAGAS 的依赖树（`datasets`/`langchain`/`rapidfuzz`/新版 `openai`）
与本项目锁定的版本冲突，**装不进去**。所以用「LLM 当裁判」按其**公开定义**在本地复刻四个指标
—— 保留的是**方法论**，不是它的代码，**数字也不与 RAGAS 可比**。

**它解决的痛点**：本项目所有质量判断原先都是**定性**的 —— 三个闸门阈值是手工标定的，
CLAUDE.md 反复写「换语料后必须重新标定」，但**没有工具能告诉你标定得好不好**；
`eval_rerank.py` 只量耗时与排序变化，不量答案质量。现在改一个旋钮跑两次，数字变好还是变差
一目了然，并且能直接指出**具体是哪几道题坏了**。

**四个指标**（每题一条记录，四项**各自独立求值、互不牵连**，一项挂掉不影响其余三项）：

| 指标 | 定义 | 实现 | LLM 调用 |
| --- | --- | --- | --- |
| `faithfulness` | 答案中**被资料支持**的陈述 / 全部陈述 | ① LLM 拆原子陈述 ② 批量判「资料能否支持」 | 1 + ⌈n/8⌉ |
| `answer_relevancy` | 从答案反推 n 个问题，与原问题的平均向量相似度 | ① 反推 3 个 ② **项目自己的 bge-small-zh** 算余弦 | 1（+本地嵌入） |
| `context_recall` | 参考答案中能归因于资料的陈述 / 全部陈述 | ① **标点切句**（不走 LLM）② 批量判归因 | ⌈m/8⌉ |
| `context_precision` | `Σ_k (precision@k × v_k) / 相关总数` | 逐条判检索结果相关与否 → 套公式 | 1 |

⚠ **`context_recall` 的切句刻意不走 LLM**，与 RAGAS 的实际做法一致（它用 NLTK 的
`SentenceTokenizer` 切参考答案，只有「归因判定」交给模型）。理由不只是省一次调用：
参考答案是**人工写的**、句子边界清楚；而 faithfulness 那一侧是模型生成的自由文本，才需要 LLM 拆。

**每题合计 ~6.2 次调用**（实测 5 题 32 次：1 次生成 + 5~6 次裁判）。
⚠ **实测全量 74 题 = 458 次调用 / 6.5 分钟**（并发 4 题 / 8 请求）—— 比按单题耗时推算的
「20 分钟」快得多，**别照单题串行时间估总时长**，并发收益几乎全在裁判那 5 次调用上。

### ⚠⚠ 空检索必须单独成桶，绝不能混进均值

闸门把「知识库没答案」的问题**整体筛空**时，模型回「根据现有资料，暂未找到明确依据」。
那句拒答是**唯一一条陈述**，而它恰好被**空上下文**支持 ⇒ **faithfulness = 1.0，满分**。
一个完全没答上来的问题拿了满分。

⇒ 判据用**结构**而非话术：`len(sources) == 0` 归入 `empty_retrieval` 桶，**四项均值把它整体排除**，
单独报出条数。⚠ 刻意**不**去匹配「暂未找到明确依据」那句话 —— 旧联网触发 ③ 上记过这条教训（话术判据会整条静默失效），见 `联网搜索与Exa.md`。**非空检索但模型仍拒答**的留在正常桶里，表现为
relevancy 偏低，那是**真实信号**（该答的没答），不该被藏起来。

| --- | --- | --- |
| 问题来源 | 语料原文 | 同一批问题**换个问法**，参考答案**原样沿用** |
| 实测检索层 | 空检索 0/74、平均命中 4.8 条、**原文命中 74/74**、MRR **0.9932**、名次 `{'1': 73, '2': 1}` | 小样 5 条同样 5/5、MRR 1.0（**五种融合配置全都一模一样**，见下节） |
| 性质 | **回归基线**，测不出检索短板 | 比基线强，但**仍偏易** |

⚠ 两份**都在天花板上**：问题原文就在索引里，检索必然命中。所以**有信号的只有相对变化**
（改一个旋钮跑两次对比）与**最差题清单**。留出集之所以仍偏易，是因为改写**保留了领域关键词**
（「单一来源采购」「联合体」），而那些词正是检索的钥匙 —— 真要变难就得换掉关键词，
但那会**改变问题本身**。这条局限写进了脚本文档字符串。

⚠⚠ 这句「有信号的只有相对变化」**已经实测撞到过墙角**：2026-09-22 调 RRF 权重时，语料与
留出集**都没有区分力**（留出集那 5 组配置全部 MRR 1.0），整轮扫描只能给出「不会更差」
这一个方向 —— 见下面「RRF 融合参数扫描」一节。**别把「跑两次对比」想得比它实际能做到的强。**

### RRF 融合参数扫描（2026-09-22 实测）

起因是一个提案：「按问题类型**动态**调 RRF 的 k 或 Dense/Sparse 权重 —— 法规类偏重 Sparse、
概念类偏重 Dense」。按仓库纪律先核实前提再动手，于是给 `eval_rag.py` 加了三个旋钮扫了一遍。
结论是**提案的前提半错，而动态那半没有可捕获的东西**。

**扫描结果**（`--no-llm --retrieval live`，零 API 成本）：

| 数据集 | k | vw | bw | MRR | 名次分布 |
| --- | --- | --- | --- | --- | --- |
| 语料 74 题 | 60 | 1 | 1 | 0.9932 | `{1:73, 2:1}` |
| 语料 74 题 | **1** | 1 | 1 | 0.9932 | `{1:73, 2:1}` |
| 语料 74 题 | 60 | 4 | 1 | 0.9932 | `{1:73, 2:1}` |
| 语料 74 题 | 60 | 1 | **4** | **1.0** | `{1:74}` |
| 语料 74 题 | 1 | 1 | **4** | **1.0** | `{1:74}` |
| 留出集 5 题 | 上述**全部**五组 | | | **1.0** | `{1:5}` |

单路基线（语料）：**BM25 单独 MRR 1.0**、向量单独 0.9932、1:1 hybrid 0.9932（= 向量单独）。

⚠⚠ **`k` 是死旋钮，别再去扫它**：`k=1` 与 `k=60` 逐字节相同。原因是归一化
`max_possible = (vw + bw) / (k + 1)`（`hybrid.py:94`）把 k 从**绝对尺度**里约掉了 ——
剩下的自由度只有**权重比**（两个权重同倍放大等于没变）。**要调就只调比例。**

**唯一量到的那道题**：`qa-0069`「输出3件安徽省最新的关于物业服务的**招标**项目」被
`qa-0070`「…**中标**项目」压到第 2 名 —— 一个字的差别。BM25 分得开（BM25 单独 1.0 就是这么
来的），1:1 融合把它稀释了，`bw=4` 把权重掰回来。

⚠⚠ **但它不在提案那根轴上**：`qa-0069` 既不是法规类也不是概念类，它是「查某一批具体项目」。
真正的判据是「**这个问句是否依赖一个精确词，去和近似重复的语料分开**」—— 那是**第三根轴**，
提案里没有它。⇒ 静态调比例已经吃掉全部量到的收益，**动态机制在这份数据上没有可捕获的对象**。

⚠⚠ **没有实现「按问句动态调权重」**，三条理由：① 上一条（唯一量到的失败不在那根轴上）；
② 它是「**服务端替模型做语义判断**」，与 `/api/chat` 那三条已删除的自动联网触发**同型**
（`工具层.md` 明写这类判据「必然静默出错」），也是「本仓库拒绝过再加一个 `is_enum_question`
式启发式」那条纪律 —— `rag.is_enum_question()` 是**唯一**的那个，别再添第二个；
③ 要让动态有得可调，前提是**先把评估集换成不饱和的**，那是另一件事。

⚠⚠ **这一轮只能说清「会不会更差」，说不清「会不会更好」** —— 留出集补测本就是为此做的，
结果它**和语料一样没有区分力**：五组配置全部 MRR 1.0、全部 `{1:5}`，**连 `--mode vector`
（被怀疑较弱的那一路）也满分**。所以它既没否证也没确认任何东西 —— 比计划里预期的「持平」
还要弱（计划原话是「掉分是可信的否决信号，**持平不是有力的支持信号**」，实测比这更空）。
⇒ 以下三件事**不要**从这份数据里读出来：别把 `bw=4` 说成「验证了稀疏加权有效」；别把语料
0.9932 → 1.0 当成「检索质量提升」的凭证（分母 74，而那 1 道题就是差异的全部）；
别指望换个数据集就自动变难（改写题**保留了领域关键词**，而那些词正是检索的钥匙）。
**这份 MRR 只能当回归基线用** —— 想真给稀疏加权定代价，得先造一份「问法不一致、且参考答案
仍可判对错」的评估集，那是另一件事。

**已落地**：`bm25_weight` 默认值 1.0 → **4.0**，三处一起改（`config.py:358` / `.env` /
`.env.example`）—— 漏 `.env` 会被它静默覆盖（本仓库记过四次的坑），依据与代价也写在那三处
的注释里。
⚠ 两个副作用要知道：① `(vw+bw)/(k+1)` 变了，`Source.rrf_score`（**原始**融合分）整体换刻度 ——
实测 `2/61=0.032787` → `5/61=0.081967`，涨的正是这个倍数。⚠ 但**面板上显示的那个百分比
（`Source.score`）几乎不动**：它是 `rrf_score / max_possible`，归一化把刻度**约掉了**，
实测同两条命中 `1.0000→1.0000`、`0.9761→0.9807`（差异只来自两路的**名次差**）。
（原先这里写的是「融合得分百分比整体换一套刻度」—— 那是**没实测的推断，实测推翻了**。）
**没有任何离线探针会因此变红** —— 全仓没有探针跑真检索，`probe_conv_store.py:610` 那个
`rrf_score` 是手搓的 payload 夹具；② **闸门不受影响** ——
`retriever._passes_gate()` 读的是 `vector_score` / `bm25_score` **原始分**、不读融合分，
所以 `MIN_VECTOR_SCORE=0.72` / `MIN_BM25_SCORE=8.0` 的标定依然有效，**不用重标**。

**验「`.env` 真的生效了」的最省办法**（比打接口直接，且不需要后端）：
`uv run python -c "from bidding_qa.config import settings; print(settings.bm25_weight)"`。
⚠ 别只跑扫描就以为验过了 —— 扫描走的是 `setattr`，**不经过 `.env`**，
恰恰绕开了「三处一起改」那个坑本身。

### 旋钮全走 CLI，`config.py` **一个字段都不加**

刻意的：本仓库记了四次的「`.env` / `.env.example` / `config.py` 三处一起改，漏一处**静默覆盖**」
陷阱，加上 `extra="ignore"` 的静默丢弃，为评估新增配置字段不划算。`--mode` / `--top-k` /
`--rerank` / `--min-vector-score` / `--min-bm25-score` / `--min-rerank-score` /
`--rrf-k` / `--vector-weight` / `--bm25-weight` /
`--concurrency`（默认 4 题）/ `--llm-concurrency`（默认 8 请求）/ `--resume` /
`--judge-thinking` / `--pipeline {chat,agent}` / `--retrieval {auto,live,http}` / `--no-llm`。

⚠ **六个阈值/融合参数的覆盖都是「改本进程的 `settings` 运行期属性」**（pydantic-settings v2
未设 `frozen`，已实测可赋值），所以它们**只对 `--retrieval live` 生效**。生效机制是
`hybrid.reciprocal_rank_fusion()` **调用期**现读 `settings.vector_weight`（`hybrid.py:36-39`）、
而 `retriever.py:94` 那个**全仓唯一**的调用点不传权重 —— 哪天有人把权重改成 import 期的
模块常量，这三个旋钮会**静默失效**。
⚠ **三个融合参数也进了 run-id**（`rk` / `vw` / `bw` 后缀），理由与三个阈值逐字相同：
不进名字就会共用一个检查点，`--resume` 把题目全部跳过，表现是「换了参数重跑，数字一模一样」。

### ⚠⚠ 走 HTTP 时扫阈值会「看起来像旋钮无效」，脚本当场报错

闸门阈值**不是请求参数**，它活在**服务端进程**的 `settings` 里。后端在跑时本地 Qdrant 的
排他锁被占，脚本会自动改走 `POST /api/search`（内部就是**同一份** `retriever.search()`，
所以检索行为是保真的）—— 但此时改本进程的 `settings.min_vector_score` 对服务端**毫无影响**。

⇒ 于是「扫一遍阈值」会产出一堆**数字完全相同**的报告，看起来像「这个旋钮没用」，
实际是**它压根没生效** —— 正是本仓库最警惕的那类静默错误。所以脚本**当场报错退出**，
并提示「要扫阈值：先停掉后端，然后 `--retrieval live`」。

⚠ 顺带一条通用约束：**跑评估之前通常要停掉后端**（本地 Qdrant 嵌入式文件模式，
同一目录独占锁，与「起了 API 就不能再 ingest」是同一条限制）。

### ⚠⚠ 检查点文件名里，四个指标的短名必须两两不同

`run-id` 由配置拼出来（不含时间戳），所以「同样的配置再跑一次」会接着上次的检查点续跑。
⚠ **不能拿 `name[:3]` 图省事**：`context_recall` 与 `context_precision` 的前三个字母都是
`con` ⇒ 两次不同的运行**共用同一个检查点文件**，后跑的覆盖先跑的，而 `--resume` 还会拿
前一份的 id 集合去跳过题目 —— 表现是「**换了指标重跑，数字一模一样**」。
所以写死一张 `_METRIC_SHORT` 表（`fai`/`rel`/`rec`/`pre`）+ **import 期 assert** 挡漏改
（照 `agent.py` 的 `QUERY_TYPE_LABELS` 惯例），并由 `--selftest` ⑫ 逐对比较所有单指标运行的名。
⚠ 同样地，**短名按 `ALL_METRICS` 的规范顺序取**，不按用户输入顺序 ——
`--metrics recall,faith` 与 `--metrics faith,recall` 是同一次运行，算出两个名字的话检查点会凭空分家。
⚠ 这个坑是**实测撞出来的**（第一版就是 `name[:3]`，跑出 `mfai-ans-con-con`）。

### 其余几条实现约束

- **裁判调用复用 `llm.stream_with_tools(tools=None, ...)`，不新建客户端、不改 `clients/` 一行**。
  ⚠ **不用 `llm.complete()`**：它不接受 `max_tokens` 覆盖（写死 `settings.deepseek_max_tokens`），
  而本项目模型是**推理型**的，思维链会先吃掉预算 —— 那个坑在 glm-4.6v 上记过一次
  （「给少了表现为返回空，最难查的那种」）。`stream_with_tools` 同时给了 `max_tokens` 与
  `disable_thinking` 两个旋钮。⚠ **`temperature` 默认 0.0 且裁判一律用默认值** ——
  同一份输入两次跑出两个判定，指标就没法用来做 A/B 了；只有 `make_eval_questions.py`
  生成改写题时传 0.9（那里**要**多样性）。
- **宽容 JSON 解析自备一份，不 import `vision._extract_json`**：它是私有函数，且返回值写死
  `dict | None`（末尾 `isinstance(data, dict)`）。而「把答案拆成陈述」返回的是 **JSON 数组**
  —— 用它会**静默返回 None**，表现是 faithfulness 整列变成 `null`，看起来像「模型不配合」。
  ⚠ 解析要两轮：默认失败后**再试 `strict=False`** —— 模型真会写出「字符串里带裸换行」的 JSON
  （JSON 规范里非法，默认解析器直接拒），一行开关就能救回来。
- **`_judge_json` 是全部裁判调用的唯一咽喉**，且**绝不抛异常**，返回 `(数据, 错误文本)`。
  「降级而非报错」放在这一层最省事：每个指标只需判 `data is None`。这也是错误原因能被如实
  记下来的唯一位置 —— 拿到的是「连接超时」还是「模型吐了段散文」，**修法完全不同**。
- **覆盖率低于一半时判「算不出来」（`None`）而不是给个低分**：裁判只判出 25% 的条目时，
  那个分数反映的是**解析坏了**而不是答案坏了。给 0.0 会被当成「答案真的很差」。
  ⚠ 这条在 `--selftest` 里踩过两次（我把 `[False, False, False, None]` 误当成「4 条只判了 3 条」，
  实际 `None` 才是唯一没判的那条，覆盖率 3/4，0.0 是**合法**分数）。
- **并发只给大模型调用**（`--llm-concurrency`，默认 8），**检索与嵌入一律串行化**
  （各一把 `asyncio.Lock`）。两个理由都是这台机器上的真实约束：① 本地 Qdrant 是**嵌入式文件
  模式**，多线程并发打它不是有文档保证的用法，而检索热了只要 15~25ms，串行化代价约等于零；
  ② **torch 的 8 个线程已被跑满**，并发嵌入只会互相抢核。⚠ 另设 `--llm-concurrency` 而不是
  让「题数 × 每题的裁判数」无限并发：4 题 × 5 个裁判 = 20 个在途请求会撞限流，而 429 的表现
  （指标静默变 null）**看起来像模型不老实**。
- **`--no-llm` 是零 API 成本的检索层**：只跑检索与打分，输出空检索率 / 命中条数 /
  原文命中率 / MRR / 名次分布。改动检索后**先跑它**，几秒出结果，不用等半小时。
- **连续 5 题一个指标都没算出来就提前中止**（`ABORT_AFTER_BARREN`）并明说原因，
  别白跑一小时 —— 那种形态基本都是 Key 失效或额度用完。
- **`use_llm=True` 是硬性的**：`not llm.ready` 时 `stream_answer` 会**静默退化成
  `fallback_answer()`**（把知识库原文原样端出来），那不是模型答案，拿去算 faithfulness 得 1.0、
  算 relevancy 毫无意义 —— 一整轮数字全废。所以 `llm.ready` 的守卫**在最前面**。
- **前端/后端零改动**：`retriever.py` / `rag.py` / `agent.py` / `api.py` / `clients/` 一行没动。
  ⚠ `--pipeline agent` 会**摘掉图谱/采购库/联网三个工具**（`_isolate_agent_tools()` 替换
  **`rag_tools.TOOL_SCHEMAS`** 与 `rag_tools.TOOL_NAMES`，并把 `graph_store.ENABLED` /
  `pg_store.ENABLED` 置假 —— `TOOL_SCHEMAS` 是 **import 期**常量，改 `ENABLED` 对工具表没用；
  好在 `tools_for()` 是**调用期**读全局，替换立刻生效）。
  ⚠⚠ **写的是 `rag_tools.`，不是 `agent.TOOL_SCHEMAS`** —— 2026-09-20 搬迁后 `agent.py` 那份
  只是**只读 re-export**，赋值给它只加了个新名字，`tools_for()` 读的仍是 `rag_tools` 的全局，
  **静默失效**：三个工具照旧挂着、图谱行与网页正文混进上下文，而四项指标看起来一切正常。
  于是测的是「只会检索的 Agent」，与线上真实形态有差异 —— 这是为了让四项指标有意义付出的代价。
- **产物落 `data/eval/`**（`<run-id>.jsonl` 逐题 + `<run-id>.summary.json` 汇总）：
  这是仓库里**第一个写结果文件的评估脚本**（其余 14 个只打 stdout）。破例是因为长跑需要检查点、
  `--resume`、以及两次运行的逐题差异对比。⚠ **没有动 `.gitignore`** —— `data/eval/` 该不该进
  版本库由用户决定。

### 两份数据集怎么用

```bash
# 语料 74 条：回归基线（不传 --questions 就从 dataset.load_qa_docs() 取）
uv run python scripts/eval_rag.py --out data/eval/baseline
uv run python scripts/eval_rag.py --rerank      --out data/eval/rerank-on     # 开重排
uv run python scripts/eval_rag.py --mode bm25   --out data/eval/bm25          # 换检索模式
uv run python scripts/eval_rag.py --no-llm                                    # 只跑检索层

# 留出集：先小样看改写质量，再决定要不要全量
uv run python scripts/make_eval_questions.py --limit 5 --out data/eval/holdout-sample5.jsonl
uv run python scripts/eval_rag.py --questions data/processed/eval_questions.jsonl
```

`eval_questions.jsonl` 是**可手工编辑的数据文件**（`{"id","question","reference","doc_id","origin"}`）：
不满意某几条直接改文本，重跑不用重新生成。`--questions` 也接受 `.txt`（一行一个问题、
没有参考答案）—— 那样 `context_recall` 自动跳过并在报告里标注。

⚠ `make_eval_questions.py` 的提示词里有三条红线，**改提示词前先读**：不许引入原问题没有的
限定条件（省份/年份/金额/主体 —— 引入就变成另一个问题，而参考答案没跟着变，那道题的
`context_recall` 会莫名偏低，看起来像检索坏了）；不许照抄原句（去标点后逐条比对，
**完全相同的丢弃并报数** —— 不丢的话那条题测的还是原文，留出集偷偷退回成基线）；
只要 JSON 数组不要围栏（⚠ 实测模型不守这条，所以解析照样走宽容路径）。
⚠ 脚本会**标出**改写里新出现的限定条件，但**只警告不丢弃** —— 那个正则会误报，
而误丢一条的代价是留出集少一条、更难发现。取舍方向与 `rag.is_enum_question()` 相反：那边宁可多判，这边宁可少扔。

### ⚠⚠ 先量噪声底，再看数字（2026-09-20 实测）

**同样是这个脚本、同一批答案、同一个提示词，连跑两次**（74 题全量重判 faithfulness）：

| | 两次运行 |
| --- | --- |
| 全量均值 | 0.9686 vs 0.9641 → 差 **0.0045** |
| 逐题分数 | **3/74 不同**，单题极差均值 **0.278**、最大 **0.333** |
| 拆出的陈述总条数 | 362 vs 369 —— **拆分步本身也有抖动** |

⇒ 两条使用纪律，**不遵守就会拿噪声当成果**：

1. **均值层面噪声底 ≈ ±0.005**，所以「改动让均值动了 0.01 以上」才值得当信号。
   低于这个数的一律当没变。
2. **单题分数噪声 ±0.28，绝不能用单题下结论。** 「优化后 qa-XXXX 从 0.5 涨到 0.75」
   这种话没有意义 —— 它完全可能是同一次运行内部的抖动。要看**题面不变时 n（陈述条数）
   有没有变**：n 变了才是机制性变化，n 没变而分数变了基本都是噪声。
   ⚠ 这条直接决定了「最差题清单」的用法：它用来**找线索**，不用来**下结论**。

⚠ 抖动的来源是**判定步**（拆句相对稳，但 74 题也会差 7 条）：`temperature=0.0` 在本项目
这个推理型模型上**不等于确定性**。`_judge_json` 的降级逻辑没错，是模型本身不可复现。

### ⚠⚠ 光杆判词：一个被修掉、且**试过错修法**的指标缺陷（2026-09-20）

**现象**：`qa-0060` 的答案几乎是参考答案原文，faithfulness 却只有 0.5。
**根因**：`SYSTEM_PROMPT` 第 5 条要求「结论先行」，模型很自然以「不可以。」起头。
LLM 把它拆成**独立一条** —— 那条既没主语也没谓项，裁判在资料里找不到任何东西能支持它，
只能判不支持。**分数测的是拆句方式，不是忠实度。**

`qa-0047` 是铁证：语料里**人工写的参考答案本人**就是
`'不可以。规模条件无论作为资格条件还是评审因素，都构成对中小企业的差别待遇或者歧视待遇。'`
—— 模型照着它作答，却因为拆句被扣分。

**修法**（两个都试了，只有一个留下）：

- ❌ **给 `_SPLIT_USER` 加一条「光杆判词不要单独成条」—— 实测要撤掉**。模型把那条
  **过度泛化**，开始**合并整句**而不是只并光杆判词：`qa-0004` 稳定地从 0.800 掉到 0.500
  （三次重跑逐字相同，**不是噪声**），因为「可以采用单一来源方式采购。」后面那一整句
  4 个 claim 被揉成一条，**一个未支持的分句污染了另外三个**。整个过程均值只 +0.0084，
  且出现回退。
- ✅ **代码侧 `_merge_short_statements()`**：只把「去标点后 <6 字」的片段并进相邻陈述
  （`_MIN_STMT_CHARS = 6`，标定依据：光杆判词 2~3 字，带上谓项「应当公开招标」6 字）。
  **精确命中、永远不动长句**。单靠它就把 qa-0060（0.500→1.000）与 qa-0047（0.667→1.000）
  治好，**不需要提示词配合**。两次重跑都触发 3 次，**变差 0 题**。

⚠ 与 `_split_sentences` 的 `>= 4` 是同一条纪律、**处置相反**：那一侧是参考答案，
噪声片段直接**丢**；这一侧**不能丢**（会静默改变 faithfulness 的分母），只能**并**。
⚠ **别再往 `_SPLIT_USER` 里加这条** —— 提示词说不清「只并那一小截」，代码能。

### 已知局限（写进脚本文档字符串了，别让人误读数字）

1. **自评偏高**：裁判与被评模型**是同一个 DeepSeek**（本机没有第二个可用的文本大模型）。
   缓解只有三条：`context_recall` 用的是**人工写的**参考答案、空检索桶是结构判据、最差题清单
   可以人工复核。**别把绝对值当权威**，**只拿同一份数据集上的相对变化做决策**。
2. **数字不可跨项目比对**：这不是 RAGAS，`answer_relevancy` 用的是 bge-small-zh 的余弦
   （RAGAS 默认 `text-embedding-ada-002`），`context_precision` 的实现也未必逐位一致。
3. **留出集不是独立评测集**：改写题由同一个模型基于原问题生成，仍偏向原问法的词汇。
4. **`--pipeline agent` 已被裁剪**（见上），与线上真实形态有差异。
5. **单次快照**：不测多轮追问、不测图片、不测 `/api/chat` 的联网分支。
6. **语料里有一条坏数据，`qa-0046`**（2026-09-20 评估跑出来的，**决定先只记录不动**）：

   ```
   问:        输出2023年上半年1-6月国内医院手机机器人招采情况详情
   参考答案:  '2023年上半年手术机器人招采情况如下：'      ← 20 字，冒号结尾，后面没有内容
   ```

   它的 `context_recall = 0.0` —— **那是指标正确地报出了坏数据**，不是检索坏了
   （同题检索命中原文、`gold_rank=1`）。问题里写「手机机器人」、参考答案写「手术机器人」，
   多半是录入错误。⚠ 它是 74 条里**唯一**这种形状的，且只把 `context_recall` 均值
   从 0.987 拉到 0.9867（0.0002）—— **它不影响任何结论**。修它要改
   `data/processed/问题答案样例数据.xlsx` 并**重新 ingest**（与后端互斥），是另一件事。

## Agent 综合评估（`eval/agent_eval.py`，2026-09-21 加）

**为什么要另起一个脚本**：`scripts/eval_rag.py --pipeline agent` **主动把三个可选工具摘掉**
（`_isolate_agent_tools()`）—— 不摘的话图谱行与网页正文混进上下文，四项指标全失去意义。
所以它测的是「**一个只会检索的 Agent**」，而 **Agent 最核心的行为（工具路由）根本没被测量**。
本脚本补的就是那一层：四个工具全挂，同时报「工具选得对不对」与「答得好不好」。

```
eval/
├─ agent_eval.py      主脚本
└─ agent_cases.jsonl  测试用例（**可手工编辑的数据文件**，加题不用改代码）
```

⚠⚠ **绝不要在这里调 `_isolate_agent_tools()`** —— 那是本脚本与那个脚本唯一的分野。

**产出**（口径与权重是**从用户给的示例数字反推验证**过的，不是随手定的）。
以下是 **2026-09-21 四个工具全部在线的真机全量**（PG 起来之后那一次）：

```
  测试用例      : 10
  工具选择准确率: 10/10 (100%)
  Faithfulness  : 0.92
  Relevancy     : 0.88
  Recall        : 0.93
  平均延迟      : 14.2s (min 2.7s, max 41.8s)
  综合评分      : 0.91 / 1.00
  Agent评分     : 0.95 (RAG权重0.6 + 工具权重0.4)
```

⚠ **这组数字的含金量低于它看起来的样子**，三件事都要知道再引用：
① 10 条样本，工具准确率**每错一题就是 10 个百分点**；
② `10/10` 里有 **5 题是「空过」**（没调任何工具，靠预检索/预联网就答了）；
③ 裁判与被评模型**是同一个 DeepSeek** —— 自评偏高。
⇒ **只看同一份用例上的相对变化，别拿绝对值当水平**（同 `eval_rag` 那两条局限）。

- **综合评分 = 三个 RAG 指标的等权均值**（**只要三项，没有 `context_precision`**）
- **Agent评分 = 0.6 × 综合评分 + 0.4 × 工具选择准确率**
- ⚠ `--selftest` ⑧ 把用户示例那组数字（`0.31/0.41/0.23→0.32`、`0.6×0.32+0.4×1.0→0.59`）
  **逐位钉死** —— 公式被顺手改掉会当场变红，而不是等数字看着不对劲才有人怀疑。

### ⚠⚠ 怎么看见 Agent 的内部状态：`RecordingLLM`（本脚本的设计核心）

SSE 事件是**冻结的前后端契约**，为评估去改它有真实回归风险。而它恰好缺了三样评估要的东西：
`tool_call.query` 是 `peek_display()` 的**展示串**而非模型给的参数、`tool_result` 不带工具
返回的正文、**没有任何事件能告诉你哪一轮被强制了**。

⚠ 顺带纠正一条流传的说法：**「强制轮不发事件」是错的**。`agent.py:359-362` 只换了流的**来源**，
那一轮照样走 `:372-457` 的公共后处理，`tool_call` / `tool_result` 正常发；看不见的只是
*「这一轮被强制过」*这件事本身。

解法是用**依赖注入那条缝**：`run_agent_stream(llm, retriever, ...)` 的**第一个参数就是 llm**
（`agent.py:219`），传一个鸭子类型的包装器进去即可 —— **零改动 `agent.py`、零改动 SSE 契约**。
`agent.py` 全路径只读 llm 的**三处**（`llm.ready` / `llm.stream_with_tools` /
`llm._NOT_CONFIGURED`），所以 `__getattr__` 转发就够。

⚠⚠ **两个必须照做的细节，错一个都是静默故障**：

1. **快照必须 `deepcopy`，不能存引用**。`messages` 是**同一个 list 对象**，
   `run_agent_stream` 每轮往它 append（`agent.py:410` / `:434`）。存引用的话五轮记下来的是
   **同一份终态** —— 前几轮的工具证据全丢，而且丢得**看不出来**：证据反而更全、
   faithfulness 更高、报告一切正常。`--selftest` ① 钉着这条。
2. **`stream_with_tools` 必须是普通 `def`**（调用方的形状是
   `async for ev in llm.stream_with_tools(...)`，**从不 await**）。普通 def 在**调用那一刻**
   就记录，时机最确定。

⚠ 包装器**刻意不继承 `BaseLLMClient`** —— 那个 ABC 的唯一消费方是类型标注，仓库里的假 LLM
全是鸭子类型（见「客户端层」那条）。
⚠ `__getattr__` 里**必须走 `self.__dict__.get("_inner")`**：写 `self._inner` 会在构造期与
`copy.deepcopy` 探测属性名时**无限递归**，栈里全是 `__getattr__`，看不出真正的原因。

### ⚠⚠ faithfulness 的判据：`--faith-context evidence`（默认）vs `sources`

Agent 链路里**图谱与采购库的结果不是 `Source`**、从不进 `sources`（理由见「引用编号」那条
不变量）。所以**只拿 `sources` 当判据的话，任何从图谱/数据库得来的答案 faithfulness 恒为 0**
——而那恰恰是本脚本存在要测的行为，是**系统性低估且报告上看不出异常**。

| 取值 | 判据 | 什么时候用 |
| --- | --- | --- |
| `evidence`（默认） | sources 的答条 + 图谱/采购库/联网工具的返回正文 | 诚实测「回答有没有超出 Agent 实际拿到的证据」 |
| `sources` | 只有 sources | 与 `eval_rag.py` 的既有数字**可比**（那边也是这个口径） |

⚠ 证据拼装时**跳过检索工具的 `role:"tool"` 正文**：它是 `build_context(fresh)` 的产出，
与 `sources` 里的答条**逐字重复**，并进去只是把同样的资料读两遍、白烧裁判预算。
⚠ 工具正文的截断用 `TOOL_CONTEXT_CHARS=4000`，**不是 `eval_rag.CONTEXT_CHARS`（1200）** ——
后者是配着语料里 500 字答条标定的，用它会把**答案引用了的那几行直接切掉**，
压低的恰好是本脚本要测的那批工具类题。

### ⚠⚠ 两条「指标在这儿没有定义」的排除规则（方向相反、性质相同）

`_in_rag_pool()` 是唯一的判据入口，**两个条件别合并**：

1. **`empty_evidence`** —— Agent 真的什么都没拿到（sources 与工具返回**双双**为空）。
   不排除的话模型那句「暂未找到依据」是唯一陈述、又恰好被空上下文「支持」，
   faithfulness 会算成 **1.0 满分**（同 `E.summarize()` 那条）。判据是**结构**，不是话术。
2. **`rag: false`**（用例字段）—— 题目本身**没有可被忠实/相关/召回的东西**。
   真机实测（ag-10 寒暄负例）：不排除的话 faithfulness **恒为 0.00** —— 「不客气」当然不会被
   预检索捞到的那两条无关资料「支持」，**那是定义使然，不是质量信号**，混进均值就是给
   综合评分**系统性压分**。这类题**路由照判**，只是不进三项均值。
   ⚠ 别拿它当「这题跑砸了、把它摘出去」的开关 —— 那样报告就成了自证清白。

### ⚠⚠ 工具选择准确率：`hit ⟺ require ⊆ called ⊆ allow`

```
hit ⟺ (require ⊆ called) and (called ⊆ allow)
```

⚠⚠ **为什么是 `allow` 而不是「期望一个工具名」**：Agent 链路里**预检索与预联网是无条件的**
（`run_agent_stream` 在模型第一轮之前就跑完），而那两步**不是工具调用**。所以对 kb / web 类题，
「模型直接作答」与「模型调了对应工具」**都是路由正确**。写成单个期望值会把正确行为判成失败。
⚠ 但图谱与采购库**没有任何东西替它们预跑**，所以那两类题的 `require` 非空 —— 不调工具是不可能
答对统计题的。
⚠ 判**集合**而非「至少包含」：多调一个 `allow` 之外的工具有是**真错**（`Agent模式.md` 明写
「一个问题不要两个工具都调」）。但**同一个工具调多次算命中**（模型自我分解是设计允许的）。
⚠ `allow` 允许**空集**（负例：纯寒暄一个工具都不许调），用来抓过度路由。

⚠⚠ **读数字前必须知道：空过会抬高这个数**。真机实测 10 题里有 **5 题**的「命中」是
**未调用任何工具**（预检索已经够用）—— 那是 `allow` 语义允许的**正确**行为，但它确实让
「100%」含金量下降。**报告每次都把空过题数打出来**（那句 ⚠ 不是注解，是读数字的前提）。
想让这个指标有区分力，用例就要偏向**没有东西替它们预跑**的那三类（图谱/采购库/联网）。

⚠ 用例里**必须**有一条 `web: true`（否则 `search_web` 压根不在 `tools_for()` 里）——
`--selftest` ⑪e 挡着。⚠ 联网是**逐题**开的（全局开则其余题的证据被网页污染、延迟也抬高）。

⚠⚠ **`enable_web` 逐题决定的另一个后果：同一题跨次跑可能翻**。ag-08 连跑三次，
`实调` 分别是 `[采购库、联网]` / `[未调工具]` / `[未调工具]` —— **判分取决于模型这次
调没调工具**，而预联网是白送的（调不调，那次搜索都已经发生过了）。看到单题翻转先想到这里，
别急着当回归。
⚠ 它同一题的 `Fait` 也跟着跳（两次可查的记录：`0.50` → `1.00`，`Rele` 同步 `0.81` → `0.89`）
—— **同一个原因**：证据里多不多一份工具正文，faithfulness 的判据就变了。
这类「判据本身随模型行为浮动」的题（含联网、含图谱/采购库）**单题分数一律不作数**，
只有一轮跑完的均值可看。
⚠⚠ **产物名不含时间戳**（`agent-{mode}-fc{faith_context}`，`eval/agent_eval.py:1225`），
且本脚本**没有 `--resume`**（照抄 `eval_rag.py` 的 run-id 成例时**抄来了命名、没抄来续跑**）
—— 所以**同配置重跑会直接覆盖上一次的 `.jsonl` / `.summary.json`**。
想留两次对比就得显式 `--out-name` 换个名字，否则回头核对「上次那题多少分」时手上什么都没有
（本轮核对 PG 停/开两次的差别时就踩了一次，第一次那份已经被盖掉）。
⚠ 别把它和 `eval_rag.py` 混：那边同配置重跑是**接着检查点续跑**（故意的），
这边是同名覆盖（也是故意的 —— 10 题跑一遍几分钟，没有续跑的必要）。

### ⚠ 三个运维前提（跑之前必须知道）

1. **必须先停掉后端**。本地 Qdrant 嵌入式模式对 `data/qdrant_local/.lock` 加排他锁；
   后端在跑时 `get_retriever()` 直接抛 `RuntimeError`，脚本**明确报错退出、不静默降级**。
   ⚠ Agent 链路**不支持 `--retrieval http`**：`run_agent_stream` 需要**真的 retriever 对象**
   （它内部自己发起检索），`POST /api/search` 给不了。
2. **Neo4j / PostgreSQL 得在跑**。脚本会**真 `warmup()` 一次**再报状态 ——
   这两个 store 是**懒连接**，不热身的话 `*_status()` 一律回「尚未建立连接」，
   那是「还没试过」**不是「连不上」**，拿它当预检会得出假警报。
   ⚠⚠ **「配了但连不上」与「没配置」的处置不同，别混**：
   - **没配置** ⇒ 依赖它的题**跳过**（`grade_routing` 返回 `None`），不计入分母；
   - **配了但连不上** ⇒ **路由分照样有效**（模型确实调了，只是工具返回 `ok=False`），
     坏的是**证据**（空的），三项 RAG 指标被拖低。
   ⇒ 报告里为此单开一行点名 —— **那是环境问题，不是 Agent 的锅**。
3. **Tavily 额度**：只有 `web: true` 的用例联网，每题 1 个 credit（空结果重试到 2~3 个）。

⚠ **PostgreSQL 是本机最容易忘的一个前提**：它是 Windows 服务 `postgresql-x64-17`，
而图谱（Neo4j）是另一个东西 —— 两个 store 各连各的。2026-09-21 首次跑评估时 PG 就是
**STOPPED**（`net start postgresql-x64-17` 报「系统错误 5。拒绝访问。」，**要管理员权限**），
`ag-06`/`ag-07` 的证据因此是空的，`ag-07` 的 `Reca` 掉到 **0.00**，报告如实点名。
用户手动启动后**同一份用例**重跑，两处差别只有 PG：

| | PG 停着 | PG 在跑 |
| --- | --- | --- |
| `ag-07` Reca | **0.00** | **0.50** |
| Recall（均值） | 0.86 | **0.93** |
| 综合评分 / Agent评分 | 0.88 / 0.93 | **0.91 / 0.95** |

⇒ **`Reca=0.00` 是一个只在题面里能看出来的信号** —— 它既可能是「模型没答」，
也可能是「工具连不上，证据是空的」，而这两者在报告正文里长得一样。
**看到某一题三项指标整列塌掉（尤其 Fait 却是 1.00），先去查那个工具连不连得上**，
别急着怀疑模型。这也是预检那行 ⚠⚠ 存在的全部意义。

### 其余几条

- **复用 `eval_rag.py`，不抄第二份**：它是 import 安全的（模块级只有 stdlib +
  `bidding_qa.config`，heavy import 全在函数内，`:1883` 有 `__main__` 守卫）。
  照 `make_eval_questions.py:57-58` 的成例往 `sys.path` 插 `src/` 与 `scripts/`。
  复用的是三个 `metric_*` 函数 + `_contexts_text`。
  ⚠ `metric_*` 已经把「降级而非报错」包在里面，返回 `{"value","coverage","n","error"}`，
  **别再 import `_judge_json` 那些私有件**。
- ⚠ 裁判调用**必须**设 `E._LLM_GATE` / `E._EMBED_LOCK`（模块级全局，`_gate()` 在**调用期**读）
  —— 不设的话本脚本的裁判调用**完全绕过 `--llm-concurrency`**，10 题 × 3 指标一股脑打出去
  撞限流，而 429 的表现（指标静默变 null）**看起来像模型不老实**。
- ⚠ **`--concurrency` 默认 1**：`run_agent_stream` 内部直接 `asyncio.to_thread(retriever.search)`
  （`agent.py:255`），**不经过** `LocalRetrieval` 那把串行化锁 —— 并发跑 Agent 等于多线程
  同时打嵌入式 Qdrant，不是有文档保证的用法。
- ⚠ **延迟取自 `done.total_ms`**（服务端自己量的 Agent 全程），**不是**包在外面的墙钟 ——
  后者会把后面三次裁判调用也算进去，出来一个「平均 40 秒」的假数，而报告上写着「平均延迟」。
- ⚠ **第 1 题背着全部冷启动成本**（模型加载/建连），而 `--concurrency 1` 意味着它一定排第一。
  实测 `min 2.7s / max 41.8s` 主要就是这个（`ag-01` 一人 41.8s，其余 2.7~24.7s）。
  延迟极差超过 8 倍时报告会自己提示一句 —— 那次正好卡在 15 倍上，提示确实打了出来。
- ⚠ **`load_cases()` 刻意不复用 `E.load_questions`**：后者返回固定 5 键的 dict，会把
  `allow` / `require` / `web` / `rag` **静默丢掉** —— 那样每条用例都退化成「不许调任何工具」
  的负例，工具准确率恒等于「模型从来不调工具」的比例，**看起来还挺合理**。
- ⚠ 产物的 `evidence` 字段**落盘前剔掉**（体积大且可重算），`.jsonl` / `.summary.json`
  都落 `data/eval/`（与 `eval_rag.py` 同一处，⚠ `.gitignore` 仍然**没有**动过）。

改 `eval/agent_eval.py` / `agent_cases.jsonl` / **`agent.py` 的 `run_agent_stream` 签名**之后跑：

```bash
PYTHONIOENCODING=utf-8 uv run python eval/agent_eval.py --selftest    # 48 条，**全离线**
uv run python eval/agent_eval.py --check-tools                        # 只报四工具可用性
uv run python eval/agent_eval.py --limit 3                            # 小样（先停后端）
uv run python eval/agent_eval.py --out data/eval                      # 全量
```

⚠ **`run_agent_stream` 的签名一改，本脚本的包装器就跟着坏** —— 它依赖「llm 是第一个位置参数」
这条缝。改签名时先跑 `--selftest`（③ 钉着 `stream_with_tools` 的调用形状）。

⚠ **不写 `PYTHONIOENCODING=utf-8` 会在 Git Bash 里得到一屏乱码**（同 `curl -d` / `psql -c`
那个 GBK 老病）。脚本自己也 `reconfigure(encoding="utf-8")` 兜了一手。

### 已知局限（写进脚本文档字符串了，别误读数字）

1. **10 条样本太小**：工具准确率每错一题就是 10 个百分点，**只用来看趋势**。用例文件随时可加题。
2. **与 `eval_rag.py` 的数字不可直接比**（那边摘了工具、口径也不同）。
   只有**同一份用例上的相对变化**有意义。判分噪声底沿用实测值：均值 ±0.005、**单题 ±0.28**。
3. **裁判与被评模型是同一个**（本机没有第二个可用文本大模型）—— 自评偏高，同 `eval_rag` 局限 1。
4. **空过会抬高工具准确率**（见上，报告每次都点名）。
5. 不测多轮对话（每题独立、`history=[]`）、不测图片。

## Agent 运行看板（`eval/dashboard.py`，2026-09-21 加）

```
==================================================
  Agent 运行看板
==================================================
  总对话数      : 2
  用户反馈      : 0 条
    👍 满意     : 0 (—)
    👎 不满意   : 0 (—)
  检索缓存      : (暂无数据)
==================================================
```

**它与 `agent_eval.py` 是评估体系互补的两半**，回答两个不同的问题：

| 脚本 | 答什么 | 数据源 | 运维前提 |
| --- | --- | --- | --- |
| `agent_eval.py` | Agent **答得好不好**（10 条固定用例 + LLM 裁判） | 语料 + 真机跑一遍 | ⚠ **必须先停后端**（Qdrant 排他锁） |
| `dashboard.py` | **线上跑成什么样**（攒了多少对话、用户满不满意） | PostgreSQL | **不用停后端**（不碰 Qdrant） |

⚠⚠ 这个差别值得单独记一笔：两个脚本都在 `eval/` 下、都读本机资源，但**只有 `agent_eval`
需要独占 Qdrant**。看板只走 `conv_store` 那条 PostgreSQL 连接，**后端在跑着也照跑** ——
所以「随时看一眼攒了多少数据」这件事没有运维成本。

### ⚠⚠ 计数走真 `count(*)`，**绝不用 `len(list_*)`**

这是本脚本存在的技术理由。`conv_store` 的两个列表函数**都封顶 500**
（`_LIST_HARD_CAP` / `_FEEDBACK_HARD_CAP`），拿 `len()` 当总数，数据长起来那天会显示一个
**看起来完全合理的错误数字**（界面写「总对话数 500」，实际 1200）—— 不报错、不截断提示，
本仓库最警惕的就是这一类。所以走 `conv_store.usage_stats()`：**五个 `count(*)` 一次往返**。

⚠ 这也是「把 SQL 放进 `conv_store.py` 而不是看板里」的理由：表结构属于 `conv_store`，
散出去一份会在字段改名时**静默**失效，而且 `probe_conv_store.py` 也够不着它。

⚠⚠ `probe_conv_store.py` ⑫ 用一个**能带小数据跑**的手法钉死这件事：把 `_LIST_HARD_CAP`
**临时压到 1**，`list_conversations()` 立刻只剩 1 条，而同一时刻 `usage_stats()` 一动不动。
两条断言各钉一半 —— 先证明钳制真的在动，再证明计数不受影响；只测后者的话，
钳制恰巧没生效时那条也会绿，测的是另一回事。**压完必须还原**（`main()` 收尾的 `cleanup()`
走的正是 `list_conversations(limit=500)`，上限留在 1 会让清理只删一条、其余**静默**残留）。

### ⚠⚠ 零反馈打 `0 (—)`，**不打 `0 (0%)`**

`0%` 的意思是「测过了，全是差评」；`—` 的意思是「还没有人评过」。两者完全不同，而
**库里现在就是后者** —— 所以零反馈不是边角情况，是**跑起来当场看到的样子**。
与 `page.tsx` 的 `webConfigured` / `historySynced`、`/api/health` 的 `llm_providers`
是同一条**三态纪律**：数据还没测出来时，一个字都不该多说。

### `检索缓存` 是一根**待接的钩子**，不是硬编码的一句假话

⚠⚠ **本仓库没有任何检索缓存子系统** —— `retriever.search()` 每次都真跑；
`grep -rn cache src/` 只命中 SSE 的 `Cache-Control` 响应头、HF 模型缓存目录、
`llm_factory` 的按供应商实例缓存、以及 `__pycache__`。所以这一行**只能**打 `(暂无数据)`：
造一个 `0% 命中` 出来是在说一件**没发生过**的事。

`_cache_stats()` 恒返回 `None`，`_cache_line(None)` 渲染成 `(暂无数据)`（**不是**在行里写死
这个字符串）。要接真东西：先给 `retriever` 加一层以 `(query, mode, top_k, rerank)` 为键的
缓存、把命中/未命中计数记下来，再让 `_cache_stats()` 返回 `{"hits": …, "misses": …}` ——
`_cache_line` 的另一支已经写好了，`--selftest` ⑤b 用替身钉着它的形状。
**别拿别的指标凑数**（那会让这一行看起来有数据、实际答的不是这个问题）。

### 几条实现约束

- **横幅是 50 个 `=`**，与 `agent_eval.py` 的宽度**不同**（那边是 60），别互相抄。
- **冒号按显示宽度对齐到第 16 列**（`unicodedata.east_asian_width`，CJK 算 2 列）。
  ⚠ 用户给的示例输出里 `检索缓存:` 那行**没对齐**（其余两行对齐了），那是手打漏的 ——
  这里一律对齐，冒号列不齐看起来像脚本有 bug。
- **`_dwidth` / `_line` 是从 `agent_eval.py` 刻意复制的 3 行**，**不要 `import` 过来**：
  那个模块 import 期会 `sys.path.insert` + 跑版本守卫（提示语还写死了 `eval/agent_eval.py`，
  从看板里炸出来会误导）+ 拖进整个 `eval_rag`。为 3 行助手付那些副作用不划算。
- ⚠ **`sys.version_info < (3, 12)` 拦一道 + `sys.stdout.reconfigure(encoding="utf-8")`**：
  前者是因为本机 PATH 上的裸 `python` 是 3.8.8（不是 `.venv` 那个），
  后者是因为 👍/👎 在 Git Bash 的 GBK 下会 `UnicodeEncodeError`（同 `curl -d` / `psql -c` 老病）。
- ⚠ **降级路径补一行诊断**（`conv_status()["detail"]`，它不抛也不触发连接）。
  psycopg 的连接错误原文是**多行**的，续行要缩进到与 `诊断: ` 之后对齐，
  否则后面几行顶到第 0 列、看起来像看板之外的东西打出来的。
- ⚠ `--selftest` ⑦ 里那条「看板自己不写 SQL」**必须只扫实现段**（`def selftest(` 之前）：
  扫全文的话，断言里的 needle 字面量**自己就在 `src` 里**，`"SELECT" not in src` 恒为假 ——
  一个**永远失败**的断言，而失败原因是它自己。（第一版就是这么写的。）
