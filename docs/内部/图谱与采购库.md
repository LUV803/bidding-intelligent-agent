# 知识图谱与采购记录库

> `CLAUDE.md` 拆出来的深潜正文（原「知识图谱」「PostgreSQL 导入」「采购记录库」三节）。
> 改 `graph_store.py` / `pg_store.py`，或任何 Cypher / SQL 之前，先把这里读完。

## 知识图谱（`graph_store.py`）

Neo4j 里是 `batch/知识图谱_导入Neo4j.py` 建的中文图模型（以「交易」为中心，8751 笔），
`graph_store.py` 把它包成 `search_knowledge_graph` 工具。**只用中文那套**——`batch/to_neo4j.py`
建的英文标签那套按供应商聚合金额会笛卡尔积（单个供应商虚高 24 倍），别混进来。
英文那套已于 2026-09-17 从 `neo4j` 库清掉（19161 节点 + 6 个 `en_*` 约束），同日又用
`CALL dbms.recreateDatabase('neo4j', {clearData: true})` **重建了存储并重新导入**。重建是必需的：
删节点后 `db.labels()` / `db.relationshipTypes()` 里的英文 token 会被回收，**属性键不会**——
Neo4j 的属性键没有元数据，引擎无从判断是否还在用（官方 KB 明说，社区 issue #10941 至今未实现），
`name` / `amount` / `id` / `tradeFrequency` 这 4 个孤儿键只能靠重建存储清除。
现库里只剩中文那套共 19161 节点 / 36003 关系，属性键只有 4 个中文的。
同时删掉了残留英文模型的 `test` 库。**重跑 `to_neo4j.py` 会把它再建出来**，要跑就用 `--database` 指到别的库。

> 重建这条路已实测可用（企业版特性，**不需要先停库**，作用于默认库 `neo4j` 也正常）：
> recreate → `batch/知识图谱_导入Neo4j.py` 重新导入 → `probe_graph_store.py` 应 37 通过。
> 全流程先在 `test` 库上跑通再动 `neo4j`，源 CSV 在 `batch/结果/`，所以重建是无损的。

**三条不变量**：

1. **绝不接受模型给的 Cypher**。`query_type` 走 `_HANDLERS` 白名单分派，未知类型返回错误文本；
   Cypher 全在模块里的常量模板中、参数全部走 `$param`。
2. **只读**：`session(default_access_mode=neo4j.READ_ACCESS)` + `session.execute_read()`。
   ⚠️ `default_access_mode` 是 **session 级**配置，传给 `GraphDatabase.driver()` 会直接抛
   `Unexpected config keys`。模板本身也都只有 `MATCH`，这是第二道防线。
3. **降级而非报错**（同 `reranker.py` 的性质）：`warmup()` 吞掉所有异常，`query()` 无论如何都返回
   一个 `GraphResult`（失败带 `ok=False` + `note`），连不上时只是图谱工具如实报告失败。
   `_bootstrap()` 里那段预热**必须保持吞异常**——它会置 `state.error` 并让整个服务 503。

**`graph_store.ENABLED` 是唯一开关**（= `NEO4J_URI` 非空）。`rag_tools.TOOL_SCHEMAS`
挂不挂这个工具、`rag.py` 提示词提不提图谱，都读它，否则会出现
「提示词让模型用图谱，工具列表里却没有」的自相矛盾。

**共 9 个查询类型**（`QUERY_TYPE_LABELS` 是全集，`_HANDLERS` 按名字分派，import 期有
`assert` 兜住两边漏改）。其中 **`top_purchasers` / `top_suppliers` 是「列举某一类实体」专用的**
（2026-09 为修「采购企业有哪些」那个 bug 加的）：`entity` 留空＝全量排行，填了＝按名称过滤。
它们与 `top_subjects` 一起属于「不需要 entity」的那组（`ENTITY_REQUIRED` 是差集算出来的，
**加新的免 entity 类型时别再写死 `- {"top_subjects"}`**）。

⚠ **这两个排行按「成交笔数」排、不是按金额**（`ORDER BY cnt DESC, amt DESC`）。别手贱改成
金额优先——源数据里有一笔 66 亿的异常交易（见下），按金额排会让它霸榜，用户问
「有哪些采购企业」第一条看到的就是那笔错账。笔数优先也与 `_QUERY_LOCATE` 对采购商/供应商
实体的既有排序约定一致。

**几个已实测的坑**：

- **`sum(DISTINCT t.交易额)` 会静默算错钱**：两笔金额相同时 DISTINCT 吃掉一笔，激光打印机
  107 笔得 921785，正确 `sum()` 是 973172（少算 5.3%，不报错）。这些查询无 fan-out 顾虑
  （每笔交易只挂 1 个供应商/采购商/所在地，MERGE 建边保证的），一律用 `sum()`。
- **空 `entity` 必须挡住**：`CONTAINS ""` 恒为真，会静默返回「交易最多」那个实体的数据 ——
  看起来完全合理的错误答案。`query()` 开头按 `ENTITY_REQUIRED` 统一拦截。
- **精确名优先于频次**：搜「打印机」时图谱里真有个叫「打印机」的节点，只按频次排会静默命中
  「激光打印机」（107 笔 > 19 笔）。`_EXACT_FIRST` 的 `CASE WHEN name = $entity` 排在频次前，
  其余候选写进 `candidates` 回给模型换名重查。
- **列表切片与 `size(字符串)` 在当前 Cypher 上不可用**（`all[0..3]` 报
  `Insufficient parameters for function 'size'`）。截断一律用参数化 `LIMIT $cap`，要长度用
  `char_length()`。
- **冷连接约 2 秒**，热查询 15–25ms，所以 `_bootstrap()` 要预热。连接失败进入
  `_FAIL_COOLDOWN=30s` 冷却，而不是永久记住（Neo4j 可能比服务晚起）也不是每次重试
  （URI 不可达时每次都要耗掉一个 `connection_timeout`）。
- ⚠ **源数据里有一笔 66 亿的异常交易**（`某县残疾人联合会`，标的物是「智力精神和重度残肢体疾人
  托养服务」，交易表行号 3121），是次高金额的 2.8 倍，**看着像录入错误**（多半多了几位）。
  **源数据没有动过**——它不影响笔数排行，但任何「按金额排行」的用法都会被它带偏，
  看到离谱数字先想到这里。

改 `graph_store.py` 或任何 Cypher 之后跑（不需要大模型）：

```bash
uv run python scripts/probe_graph_store.py   # 9 个查询类型 + 金额回归 + 只读防线 + 降级
python scripts/probe_graph_tool.py           # 真机验证模型会在对的时机选对工具（需 Neo4j + API Key）
```

## PostgreSQL 导入（`src/database/to_postgresql.py`）

独立脚本，**不在问答链路里**：弹窗选一个 xlsx，整表灌进本机 PostgreSQL 的 `chatbot` 库
（`bid_records` 表，一张平表，19 列照搬 Excel 列名）。骨架照 `batch/to_neo4j.py`
（选文件 → 注入数据库的既有惯例），凭据读 `.env` 的 `POSTGRES_*`。

**默认是整表替换**（单事务 `TRUNCATE` + `COPY`），不是追加 —— 这份 xlsx 是快照且没有可靠
业务主键（「项目编号」116 行为空，做不了主键），没法 upsert。要追加得显式加 `--keep`。

几个坑：

- **`PROJECT_ROOT` 是 `parents[2]`，不是 `parents[1]`**。本文件在 `src/database/` 下，
  比 `batch/` 下的脚本深一层。写错**不报错**，只是 `.env` 和默认 xlsx 全都找不到、路径全空。
- **中文标识符一律双引号**。PostgreSQL 允许非 ASCII 列名，不加引号会做大小写折叠；中文没有
  大小写所以能过，但列名里混进大写拉丁字母或空格就会**静默**错位。DDL 与 COPY 的列清单
  都从同一个 `COLUMN_TYPES` 生成，不手抄两遍。
- **numpy 标量不能直接喂 psycopg**：`df.to_dict("records")` 给的是 `numpy.float64`，
  psycopg 会抛 `cannot adapt type`。且空值有 `None` / `NaN` / `NaT` 三副面孔，
  而 **`float('nan')` 在 Python 里是真值**，判 `is None` 会全部放行 → 库里出现字符串 `'nan'`。
  逐格走 `CONVERTERS` 显式转换，金额转 `Decimal` 而不是 `float`。
- **`CREATE DATABASE` 没有 `IF NOT EXISTS`，也不能在事务块里执行**。先查 `pg_database`，
  再用 `autocommit=True` 连过去建。
- **改列定义要重建表**：`CREATE TABLE IF NOT EXISTS` 对已存在的表是空操作，不补列也不改列。
  `check_schema()` 会在列对不上时拒绝写入（COPY 按列名错位是**静默**的，必须挡住）。
- 写入后脚本会自己复核一遍（行数 / 每列空值数 / 金额合计），但那是自证。要独立确认用 psql。

> ⚠ **Windows Git Bash 里 `psql -c "…中文…"` 会 400 级失败**（`invalid byte sequence for
> encoding "UTF8"`）：bash 把参数按 GBK 发出去，和 CLAUDE.md 上面 `curl -d` 那条是同一个病。
> 中文 SQL 写成 UTF-8 文件后用 `psql -f file.sql`，并设 `PGCLIENTENCODING=UTF8`。

本实例：`localhost:5432`，PostgreSQL 17.11，UTF8，装在 `D:\postgresql`（服务
`postgresql-x64-17`），`psql.exe` 在 `D:\postgresql\bin\`。`.env` 里的 `POSTGRES_PASSWORD`
是真实凭据。

## 采购记录库（`pg_store.py`）

同一个 `bid_records` 表（与图谱**同源**：上一节那份 xlsx 就是图谱的源数据），
`pg_store.py` 把它包成 `search_procurement_records` 工具。它与 `graph_store.py` 是同构复制：
`ENABLED` 开关、懒连接 + 30 秒冷却、`warmup()` 吞异常、`query()` 永不抛、渲染与结构化结果分离。

**查询方式 = 结构化过滤器 + 代码拼 SQL**（不是让模型写 SQL）：模型只能填结构化参数
（`contains`/`purchaser`/`province`/`amount_min`/`date_from`/`sort_by`/`group_by`/`max_rows`…），
SQL 由代码从**白名单列名**（`COLS` / `GROUP_COLS` / `TEXT_COLS` / `SORT_COLS` 的 dict 查找）拼、
值全走 `%s`。**模型给的字符串永远不进入 SQL 文本** —— 这与图谱「绝不接受模型给的 Cypher」
是同一条铁律的不同实现：那边靠枚举 `query_type` 收窄，这边靠「列名白名单 + 值参数化」收窄。

**三条不变量**（与图谱逐条对应）：

1. **只读** —— 但⚠ **`conn.read_only = True` 在 `autocommit=True` 下是个假防线**：实测它读完
   返回 `True`，服务端 `default_transaction_read_only` 仍是 `off`，`DELETE` **照样放行**
   （psycopg3 只对它自己显式开启的事务应用这个特征，而 autocommit 下它从不发 `BEGIN`）。
   **采用连接参数方式**：`options="-c default_transaction_read_only=on -c statement_timeout=…"`
   （建连时就生效，与语句顺序、autocommit 取值都无关），再加建连后 `_assert_read_only()`
   自检 `SHOW default_transaction_read_only`。模板本身也都只有 `SELECT`，这是第三道防线。
   **任何「设置了就算数」的安全断言都要先验一把** —— `probe_pg_store.py` ⑦ 断言的是
   **行为**（真连上执行 `DELETE FROM bid_records WHERE false` 必须抛异常），
   **不是** `assert conn.read_only is True`，后者在防线失效时同样返回 `True`，只制造安全感。
2. **`count(*)` 拿精确总数**，不做图谱那套 `total_capped`「下限」记账 —— SQL 的 `count(*)`
   在 8751 行上毫秒级且精确，只保留 `truncated = total > len(rows)`。
3. **降级而非报错**：`query()` 无论如何都返回 `PgResult`（失败带 `ok=False` + `note`）。
   `api.py` 里那段预热**必须保持吞异常**（它有自己的 try，**绝不写 `state.error`** ——
   那是让整个服务 503 的开关）。

**`pg_store.ENABLED` 是唯一开关**（= `POSTGRES_HOST` 非空），`rag_tools.TOOL_SCHEMAS`
挂不挂这个工具、`rag.py` 提示词提不提它，都读它。

**几个已实测的坑**：

- **NULL 组会霸榜**：`GROUP BY` 可空列时 NULL 自成一桶。`代理机构` 7698/8751 为空，排出来
  第一名是「（空）7698 条」。聚合模式一律 `WHERE 列 IS NOT NULL` 并在 note 里说明排除了多少行，
  且 **`group_by` 的候选里根本不放 `agency`**。
- **`ORDER BY … DESC` 在 PostgreSQL 里 NULL 排最前**，可空排序键一律加 `NULLS LAST`，
  另加稳定次序键避免同分抖动。
- **`ILIKE` 通配符要转义**：裸的 `'%%%'` 命中 8751 行（全表），转义后的 `'%\%%'` 命中 0 行 ——
  与图谱「空 entity」是同一类静默错答案。`\`、`%`、`_` 逐个转义 + `ESCAPE '\'`。
- **空筛选必须挡住**：一个条件都不给 = 全表 8751 行，模型会当成「你要的都在里面」。
  ⚠ 但判据是「**模型有没有说清它要什么**」而非「有没有筛选」—— 只有 `sort_by` 也算
  （「中标金额最高的项目是哪个」就是这么问的）。
- **非法筛选值必须报错而非忽略**（`amount_min="50万"` 解析不出、`group_by="星座"`）：
  静默忽略一个筛选项 = 给出一个**看起来完全合理**的错误答案。解析本身要宽容
  （`万/亿` 倍数、千分位逗号、`元`、`YYYY-MM-DD` / `YYYY/M/D` / `YYYY年M月`）。
- **数据画像决定了 `group_by` 的候选**：省份 99.2% 是安徽、发布时间只有 12 个不同日期 ——
  按这两个分组出来都是一行，**不是报错，是看起来完全合理的废话**，比报错更难发现。
  所以 `GROUP_COLS` 里没有 `province` / `year`，但 `province` 作为**筛选**保留。
  这条标定与 `MIN_VECTOR_SCORE` 同一性质：**针对当前语料实测，重新导入后要重测**
  （`probe_pg_store.py` 里有画像断言，画像变了会被测出来）。
- **`sum(DISTINCT …)` 别用**（图谱那条教训的同一条）：两笔金额相同时会静默少算。
  这里无 fan-out 顾虑，一律 `sum()`。
- ⚠ **66 亿那笔错账在这张表里同样存在**（与图谱那笔**是同一笔**，同源数据）：图谱那边靠
  「按笔数排」绕开它，但这里**不能照搬** —— 「中标金额最高的项目是哪个」是用户会真问的问题，
  按笔数排是答非所问。做法是 `sort_by` **默认 `published`**，用户明确要金额排行时照排，
  但 `render_for_model()` 里加一条**数据驱动**的提醒（金额 ≥ 50 亿时附「疑似录入错误，请向用户
  说明存疑」），不命中就不出现。
- **`statement_timeout` 是唯一的查询级超时**：`execute_tool` 自己没有任何超时，浏览器是唯一的
  取消手段。所以它必须建连时就设上，不能靠调用方记得设。
- **Cursor 不是线程安全的**：`asyncio.to_thread` 并发下 psycopg `Connection` 自带内部锁可安全
  共享，但 `_run()` **必须每次新建游标**，不复用。
- **命中 0 行时要给出自我纠正的线索**：低基数字段（省份/类别/来源）筛出 0 行时，在 note 里附上
  该列的**真实取值列表**（`SELECT DISTINCT` 毫秒级）。这是模型在**同一轮内**自我纠正的最便宜
  手段（照 `graph_store` 的 `_CATEGORY_HINTS` 思路）。
  ⚠ 但它只覆盖「筛选值写错」，**覆盖不了「问题本身需要拆成几问」** —— 后者是 2026-09-20
  把 `agent_max_rounds` 从 3 提到 5 的直接原因，别再把这条当成「轮数够用」的理由。

改 `pg_store.py` 或任何 SQL 之后跑（不需要大模型）：

```bash
uv run python scripts/probe_pg_store.py   # 9 组断言：画像对账 + 只读行为 + 注入 + 降级
uv run python scripts/probe_pg_tool.py    # 真机验证模型会在对的时机选对工具（需 PostgreSQL + API Key）
```

`probe_pg_store.py` ② 里有一条**跨技术栈对账**最有力：`标的物='激光打印机'` 的
`count(*) == 107` 且 `sum("中标金额") == 973172.0`，与 `probe_graph_store.py` 里那个
`LASER_TOTAL` 常数**互相印证** —— 两套独立技术栈（Neo4j / PostgreSQL）算出同一个数。

⚠ `probe_pg_tool.py` 的用例 ①（「中国科学技术大学采购过哪些项目？」）**会偶发不通过，
那不是回归**（2026-09-20 实测 5 次：3 次图谱 / 2 次数据库）。它正是上面「重叠区」那条：
图谱与数据库**都能答**，提示词把实体/名单类推给图谱，而问句里的「采购过哪些项目」
又确实是个带条件的筛选，模型在两者间摇摆。**别为了让它变绿去改提示词路由** ——
那会动摇「实体/名单归图谱」，而 `is_enum_question` 的强制首轮兜底正是靠它成立的。
判断它有没有真坏，看**长期**是否明显偏离 50/50，不是单次结果；用例标签里写了「⚠ 重叠区，偶发」。
