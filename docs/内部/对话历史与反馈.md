# 对话历史与用户反馈

> `CLAUDE.md` 拆出来的深潜正文（原「对话历史持久化」「用户反馈」两节）。
> 改 `conv_store.py` 或任何 SQL 之前，先把这里读完。

## 对话历史持久化（`conv_store.py`）

对话原先**只存在浏览器的 localStorage**（`bidding-qa-conversations`），三个真实痛点：
① 写失败是**静默**的（5MB 配额、单条对话可达几百 KB），表现是「历史莫名其妙少了」；
② 换浏览器/清缓存即归零；③ 完全没有搜索。现在**服务端为主、localStorage 降为降级回退**。

**身份模型是「单用户共享」**（2026-09-20 用户选定）：没有用户表、没有登录、没有 `user_id` 列，
一张表装所有人的对话，谁打开都看到同一份。日后要做登录：**加列 + 加 WHERE** 即可，表结构不用动。

⚠ **本方案不改 `/api/chat` 与 `/api/agent` 一个字节** —— 持久化整个发生在前端与那几个新路由上，
两条问答链路的 SSE 契约、请求体、事件序列原样。

### 与 `pg_store.py` 的**只读 / 可写分工**（最要紧的一条）

`bid_records` 表（8751 行，见「采购记录库」）由**两个模块读**，各有各的连接、**互不相干**：

| | `pg_store.py` | `conv_store.py` |
| --- | --- | --- |
| 用途 | 采购记录查询**工具**（模型能影响列名/值） | 对话历史（写入的是前端数据，**与模型无关**） |
| 连接参数 | `options="-c default_transaction_read_only=on …"` | **刻意没有**，它必须能写 |
| 建连自检 | `_assert_read_only()` 不过就抛 | 没有 |
| 失败形态 | **永不抛**，`ok=False` + `note` | **抛** `ConvStoreUnavailable` → 路由 503 |

**加了一条可写连接会不会把采购工具的只读保护拆掉？——不会**，`_run()` 只操作自己模块的
`_conn`，两条连接各自独立。但这是「加写连接」唯一的风险点，所以由**行为断言**钉死：
`probe_conv_store.py` ⑩ 两头都钉：在 `pg_store` 那条连接上 `DELETE FROM bid_records WHERE false`
必须**被拒**，在 `conv_store` 那条连接上 `SHOW default_transaction_read_only` 必须回 `off`。
⚠ 两条都**断言行为、不断言源码文本**：`conv_store.py` 的注释里就写着
`default_transaction_read_only`（解释为什么不用它），文本检查会被自己的注释绊倒。

**错误形态刻意与 `pg_store` 不同，别「统一」回去**：`pg_store.query()` 永不抛是**工具契约**
逼出来的（CLAUDE.md 不变量 ①：漏掉 `role:"tool"` 消息会让下一轮请求 400）；`conv_store`
**不是工具**，调用方是路由函数，抛异常才是对的形状 —— 与 `/api/vision` 的
`analyze()` 抛错 → 路由转 503 是同一个先例。⚠ **任何 psycopg 异常都要先包成
`ConvStoreUnavailable`**（`_guard()` 统一出口），别把裸的 `OperationalError` 漏到路由层
（前端会拿到一串英文连接串，还带着主机名）。

### 表结构：`payload jsonb` + 两个生成列

```sql
conversations (id text PK, title text, created_at timestamptz, updated_at timestamptz)
messages (conversation_id → 级联删除, id text, seq integer, payload jsonb,
          role    text GENERATED ALWAYS AS (payload->>'role')    STORED,
          content text GENERATED ALWAYS AS (payload->>'content') STORED,
          PRIMARY KEY (conversation_id, id))
```

- **整个前端 `Message` 对象原样进 `payload`** —— 前端以后给 Message 加字段（像上次加 `image`
  那样）**不用改表**。`schemas.py` 的 `ConversationUpsert.messages` 因此是
  `list[dict[str, Any]]` 而**不是**严格的 `Message` 模型：后者会把新字段**静默丢掉**。
  `probe_conv_store.py` ③ 拿一个 `future_field` 钉着这条。
- **`role` / `content` 是 `GENERATED ALWAYS AS … STORED` 的真列**，可直接 `ILIKE`，
  **且与 payload 不可能漂移**（列与 JSON 各存一份才会）。
  ⚠ 生成列只能引用**同一 CREATE TABLE 里已经声明过**的列 —— `payload` 挪到生成列后面
  会让建表直接报 `UndefinedColumn`，而那是**静默降级**（`_guard` 包成 unavailable
  → 前端整个历史功能变成「未同步」）。顺序是硬约束，② 钉着它。
- **`timestamptz` 而不是 bigint epoch 毫秒**：库里可读（psql 里是 `2026-09-20 10:00:00+08`）。
  ⚠ 代价是**必须在 `conv_store` 边界上转掉**（`_to_ts` / `_to_ms`）—— `datetime` 不是
  JSON 可序列化的，漏了会在 `api.py` 那句 `json.dumps` 处炸（`Decimal`/`date` 老坑，**第五次**）。
  `_to_ms` 用 `round` 不用 `int()`：截断会让写进去再读出来差 1 毫秒，往返断言永远过不了。
- **没有迁移框架**（本项目至今没有）。`CREATE TABLE IF NOT EXISTS` 对已存在的表是**空操作**，
  既不补列也不改列 —— 改列定义仍需**手工 DROP + CREATE**（与 `to_postgresql.py` 同一条坑）。

**`ensure_schema()` 是懒确保、由 `_get_conn()` 在建连后调用**（`_schema_ready` 标志 +
双检锁，每进程一次）。⚠ 若只在**写入时**建表，`/api/conversations` 的第一次读就是
`UndefinedTable` → 前端进降级模式，**而且会一直降级到有人手动跑脚本为止**（表永远建不出来）。
**读路径必须也能建。**

**`_op_lock` 串行化所有数据库操作**（`pg_store` 没有，这是又一处刻意不同）：写入走
`with conn.transaction():`，upsert + DELETE + INSERT 三句**必须原子**，否则崩在中间会留下
一条**一条消息都没有的对话**。而连接是**共享**的 —— 一个线程开了显式事务后，另一个线程的
读语句会**加入那个事务**，看见「消息已删、还没重插」的中间状态。单用户 + 毫秒级查询，
串行化的代价是零。

### 6 个端点（本仓库**第一次**出现 PUT / DELETE / 路径参数）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/conversations` | 列表，**只回元数据** + `message_count` |
| GET | `/api/conversations/search?q=&limit=` | 搜索，回元数据 + `snippet` |
| GET | `/api/conversations/{id}` | 单条的**完整正文** |
| PUT | `/api/conversations/{id}` | 整体 upsert（单事务） |
| DELETE | `/api/conversations/{id}` | 删除（级联删消息），**幂等** |
| DELETE | `/api/conversations` | **清空全部**（级联删消息，`feedback` 不动），**幂等** |

- ⚠⚠ **六条都不调 `_require_ready()`**（照 `/api/vision` 的先例）。对历史这条**更硬**：
  索引 + 向量模型加载要几十秒，若跟着 503，**首屏历史会消失几十秒** —— 而 localStorage
  版本是**秒出**的，那是明确的退步。
- ⚠⚠ **`/api/conversations/search` 必须声明在 `/api/conversations/{conv_id}` 之前**。
  FastAPI 按声明顺序匹配，反了的话搜一个词会被当成搜 `id="search"` 的对话，
  表现是「**搜索永远没有结果**」——完全静默。① 钉着这条。
- **列表只回元数据是刻意的**：正文可达几百 KB（12 条 `sources`、`steps[].pg` 整行原文、
  `reasoning` 全文、`image.full_text`），首屏全拉下来「历史秒出」就没了。正文按需取。
- **404 与 503 必须分开**：`get_conversation` 返回 `None` → **404**（这条对话不存在），
  连不上 → **503**。都塌成 503 的话前端分不出「删过了」和「数据库挂了」，
  后者会让它切进降级模式。用 200 + `ok:false` 也不行 —— `lib/api.ts` 所有辅助函数都是
  `if (!response.ok) throw`，返回 200 会让它们以为成功。
- **删除是幂等的**（删不存在的 id 是空操作）：前端删除是「本地立刻消失 + 补一发 DELETE」，
  重复发是常态。
- `_bootstrap()` 里加了**第三个内层 try**（`state.stage = "connecting_history"`），
  与 graph / pg 两段同构：**绝不写 `state.error`**（写进去 = 整个服务 503）。
- **搜索用 `ILIKE '%…%'` 而不是全文检索**：本机 PostgreSQL 没装 zhparser / pg_jieba，
  中文没法分词，`to_tsvector` 根本用不了。通配符转义**复用 `pg_store._like`**
  （⚠ 是**同一个函数对象**，别抄第二份 —— `search_conversations` 的 SQL 里写死了
  `ESCAPE '\'`，两边必须一致）。不转义的话用户搜一个 `%` 会命中**全表** —— 与图谱
  「空 entity」、`pg_store`「空筛选」是同一类**看起来完全合理的错误答案**。⑦ 钉着这条。

### 点搜索结果 → 跳到命中的那条消息 + 标黄关键词（2026-09-21 加）

原先点一条搜索结果只是**切过去**，而切换后视口停在对话**底部**（自动滚到底）——
长对话里等于「搜到了，但你自己去找吧」。现在滚到命中的那条并把它标黄。

**后端只多一个字段**：`ConversationHit.hit_message_id`（`schemas.py`），取自
`search_conversations()` 那个 LATERAL 的第三列。⚠⚠ **它必须与 `snippet` 来自同一个
LATERAL 行**（都是 `h.*`）——`snippet` 说「提问里命中了」而跳转却落在别处，就是两次
独立查询才会有的错位。⑦ 专门有一条拿「m1 与 m2 都命中」的用例钉这个同源性。

- **标题命中时 `hit_message_id` 是空串**（那时整个 LATERAL 是 NULL），前端据此**不跳转**、
  按老行为切过去。⚠ 别退化成「取第一条消息」：那是猜，会把用户送到一个与关键词
  毫无关系的位置 —— 与「空 entity 静默返回头名实体」是同一类错误。
  ⚠ 也别用「`message_id` 非空」去判断命中落在正文还是标题（`snippet_role` 才是那个信号），
  这个字段**只表示「跳到哪一条」**。

**前端是一条七处的链**（漏一处都是静默失效）：

```
conv_store(SQL) → schemas → types.ts → api.ts → Sidebar → useChat.pendingJump → page.tsx
```

⚠⚠ **`page.tsx` 的 `onSelect={(id, jump) => …}` 里那个 `jump` 不能省**。写成 `(id) => …`
**TypeScript 不会报错**（少形参对函数类型是合法赋值），`tsc` 一片绿，而运行时参数直接被丢
—— 表现是「点了搜索结果只切对话、不跳」，看不出是哪一层吃掉的。（这条是本次写完 tsc 通过
后**读代码**发现的，类型检查在这件事上帮不了忙。）

⚠ `Sidebar` 那行点击处理器里**必须在 `clearSearch()` 之前读 `query.trim()`** 并随行带上：
搜索态一清，该标哪个词就没处可查了（`SearchJump.keyword` 存在的全部理由）。

⚠ `useChat.selectConversation` 里的 `setPendingJump` **必须落在 `id === activeIdRef.current`
那个早退之前** —— 搜的恰好是当前这条对话时它直接 return，写在后面这次跳转整个丢掉。

**两个 effect 抢同一个滚动容器，是本功能最容易踩的地方**（`page.tsx`）：

- 点结果时目标对话可能**刚切过来**，于是「自动滚到底」与「定位跳转」在**同一次 commit**
  里都触发、都去滚 `scrollRef` —— 谁后跑谁赢，而结果只取决于 effect 的声明顺序。
  所以自动滚动那条**第一件事就是 `if (jumpRef.current) return;`**。
- ⚠⚠ **用 `jumpRef` 而不是把 `pendingJump` 塞进依赖数组**：进了依赖的话
  `clearPendingJump()` 会让它**再跑一次**，把视口又拽回底部 —— 前功尽弃。
  同理那条 `clearKeywordHighlight()` 写在 `return` **之后**，跳转时不执行。
- ⚠ 清高亮的那条 effect（`[activeId]`）**必须声明在定位 effect 之前**：两条在同一次 commit
  里都跑时按声明顺序执行，反过来的话「先标黄、再被清掉」，表现只是「跳过去了但没标黄」。
- ⚠⚠ **`JUMP_GIVEUP_MS` 那个超时兜底不是可选项**：`remote` 对话的正文要等
  `openConversation()` 拉回来，这一趟必然找不到元素。而一个**一直挂着的 `pendingJump`
  会让自动滚到底永远让位** —— 症状是「之后新消息再也不自动跟到最新」，一个与搜索
  毫无关系的怪症状。超时到了就 `clearPendingJump()` 收口。

**高亮用 CSS Custom Highlight API，不是插 `<mark>`**（`lib/highlight.ts`）：
消息正文是 **Markdown 渲染**的，在解析前注入 `<mark>` 会破坏代码块 / URL / 表格行。
`CSS.highlights` + `Range` 完全不碰 DOM，React 与 Markdown 各自照旧。

- ⚠⚠ `globals.css` 里那个 `::highlight(conv-hit)` 的名字**必须与 `HIGHLIGHT_NAME` 逐字一致**
  —— 对不上的表现是「滚动到了、但什么都没标黄」，既不报错也无从察觉。
- ⚠ 它的属性支持面比 `.kw-mark` **窄得多**：只认 color / background-color /
  text-decoration* / text-shadow，`border-radius` / `padding` / `font-weight` 写了
  **一律无效且不报错**。所以透明度调过（0.22 vs 0.14，那边有 padding 撑面积）。
- ⚠ 空 needle 会让 `indexOf` 循环原地打转，守卫 `if (!reg || !Ctor || !needle) return 0;`
  在**建 TreeWalker 之前**。
- ⚠ **降级而非报错**：Markdown 可能把词拆开（`履约**保证**金`）而标不到，
  那时**滚动照样生效**，只是没标黄。返回值（标了几处）调用方用不上。

锚点是 `msg-<message.id>`（`ChatMessage.tsx` 两个根节点各一个），
与来源面板的 `source-<id>-<n>` 同一套命名 —— **别改名**，`page.tsx` 按它 `getElementById`。


⚠ 这个探针的 `main()` **比 `probe_pg_store.py` 多一步**：①②⑨⑪ 四条**离线断言跑在

一旦连不上就 `return 1`，那几条在那里永远跑不到。测试数据一律用 `probe-conv-` 前缀，
跑完自己清干净（`finally` 里清，崩在半路也不留残留）。

⚠ ⑪ 用 `TestClient` 配**替身 store** 验「异常 → HTTP 状态码」的映射，**不进 `with`**：
进入上下文会跑 lifespan → `_bootstrap()` → 加载索引与向量模型（几十秒）。不进入正好
还多验一条 —— 这几条路由**不依赖启动完成**（它们刻意不调 `_require_ready()`，
否则重启后端后头几十秒首屏历史会消失）。三条判据：503 与 404 分开（前者触发整体降级、
后者不该）、空 `q` 是 400 且**在碰 store 之前**就拒（守卫顺序）、时间戳出网是 **int**
（前端拿它排序，字符串会**静默**按字典序排出乱序）。

### 前端：**同步边界是「一轮回答结束」，不是每次状态变化**（最容易被「优化」错的一处）

⚠⚠ `patchMessage` **每个 SSE 事件调用一次**（`delta` 与 `reasoning` 各一个分片），
**一轮回答就是几百到几千次**。若把落盘 effect 换成网络请求、去掉 `streaming` 守卫，
一轮问答会打出上千个 PUT。

正确的写法是**靠 `streaming` 守卫、零防抖**：流式期间那个 effect 每次都**早退**；
`run()` 的 `finally` 里 `setStreaming(false)` 与最后一个 `patchMessage` 在**同一次 commit**
落地，effect 因此**恰好在轮末跑一次**，拿到的就是终态。**零防抖、零定时器**。

配套的两条：

- **`syncedRef` 用对象身份判「脏」，不是 `updatedAt`**：`regenerate` 的截断与
  `run()` 的占位追加**都不 bump `updatedAt`**。身份比较天然覆盖。
- **写入器是单飞的**（`flushingRef` + `pendingRef` 队列）：这不是性能优化而是**正确性**
  要求 —— 两个并发的 PUT **没有先后保证**，晚到的那个若是旧内容，会把完整答案
  **永久覆盖**成截断版。`stop()` 因此**不再 `setStreaming(false)`**（只 abort），
  让「停止」也收口到 `run()` 的 `finally` 那一次，这也是那个 `finally` 存在的意义。

### `Conversation.remote` —— 一个标志，**三个守卫**

`GET /api/conversations` 只回元数据，正文按需拉。于是会存在「`messages` 是空数组、
但这**不是**真的没有消息」的对话，`remote: true` 标记它。**三个守卫缺一个都是静默的数据销毁**：

1. **PUT 守卫**：`remote` 的对话绝不能上传 —— `messages: []` 会把服务端正文**覆盖成空**。
2. **localStorage 守卫**：落盘时跳过。否则一个只拉到元数据的对话会以空正文落盘，
   **把上一轮会话存下来的那份好数据覆盖掉**，降级回退路径就在那一刻失效。
3. **`send()` 守卫**：不能在未加载的对话上提问 —— 历史被当成空数组送给模型（前几轮凭空消失），
   且因为守卫 1 它**永远不会被同步**。

⚠ 它**不进 localStorage**（与守卫 2 是同一件事的两面）：刷新后本地那份没有 `remote`，
服务端那份由启动时的 `listConversations` 重新标上。
⚠ `page.tsx` 那段 `activeConversation?.remote` 的**加载中分支必须排在 `messageCount === 0` 前面**
—— 落到下面会渲染**欢迎页**（还带示例卡片），用户点了历史却看到「开始新对话」，看起来就像记录丢了。

### 启动时序与降级

1. 照旧读 localStorage → **首屏秒出**（这一步不动）。
2. 再 `listConversations()`：
   - **成功** → 按 id **并集合并**（本地有、服务端没有的，由下面的同步扫描 PUT 上去）。
     **幂等**（跑过一次后永远是空集）、**不需要迁移标志**、升级路径无损，而且**它同时是
     自愈机制** —— 某一轮 PUT 失败过（服务端抖了一下），下一轮启动自动补上。
   - **失败** → 保留本地数据，`historySynced = false`，**不改 `activeId`**。

⚠⚠ **那处「标记成已同步」（`syncedRef.current.set(server.id, local)`）必须带条件**，
判据是 `local.updatedAt <= server.updatedAt`（2026-09-20 修）。标记的作用是**抑制重传**
（本地那份就是刚 PUT 上去的那一份，重传是 50 条 × 几百 KB 的纯浪费），但**无条件打**
会让「本地更新」的那种（服务端不可达期间问过一轮）也被跳过 —— **那一轮永远补不进
数据库**，上面那句「它同时是自愈机制」就成了一句空话（原先正是无条件标记，那条自愈
路径实际不存在）。反过来，本地**更旧**时也要照打：那时再传一次等于拿旧正文覆盖服务端
较新的那一份，是实打实的数据销毁。**两个方向都得挡住，所以判据不能省。**

### 点开历史对话时要跟服务端核对（`refreshConversation()`）

⚠⚠ **这是「点开历史对话，同一句提问出现两次」那个报障的落点**（2026-09-20 修）。

启动合并之后，**每条对话都成了「本地」的** —— `mergeServerList` 保留的是本地对象、
`remote` 被抹掉了。于是 `selectConversation` 的快路径（`known && !known.remote`）
**对每条对话都成立，服务端那一份正文永远不再被读过**。本地那份一旦被污染（重复的
用户消息、截断的正文）或过期，**界面永远显示那一份、刷新也不会好**（合并又偏好本地），
而库里那份干净数据一次都没被读过 —— 用户看到的「多点一次就多一条」，其实是「点开
看到的始终是本地那份坏数据」。

⇒ `selectConversation` 在 `setActiveId(id)` 之后**再调一次 `refreshConversation(id)`**：
界面不等它（本地那份先画出来，离线也照用），拿到服务端那份后按 `updatedAt` 决定是否替换。

⚠ **判据是 `updatedAt`，不能写成「拉回来就替换」**：

- **本地更新** ⇒ 不替换。这一条**同时就是流式安全的守卫**：正在输出时 `patchMessage`
  每个分片都会把 `updatedAt` 撞到最新，所以服务端那份必然更旧 ⇒ 不会把在途的回答
  整个抹掉。**不需要额外的 `streamingRef`。**
- **相等** ⇒ 内容本该一致，替换是空操作；顺手把「时间戳没变但内容被污染」那种一起修掉
  （重复追加若不 bump `updatedAt` 就是这副形状 —— `run()` 的占位符追加与 `regenerate`
  的截断都不 bump）。
- **服务端更新** ⇒ 替换，并把新那份标记成已同步（不再重传）。

时间戳能这么用，是因为 PUT 把客户端的 ms 原样存进 `timestamptz`、读回来 `round()`
还原为**逐毫秒相等**（`probe_conv_store.py` ⑧ 钉着这条）。

⚠ 失败（404 / 连不上）**什么都不做**：本地那份照旧，也不动 `serverMode`（404 ≠ 数据库挂了）。
⚠ 用户**从没上传过**的本地对话（新建、还没跑完一轮）会 404，白白一次请求，可接受。

`historySynced` 是**三态**（`null` = 还没结论，侧栏**一个字都不说**）—— 同
`page.tsx` 的 `webConfigured` 约定。⚠ 它读的是 **`listConversations()` 那一次调用的成败**，
**不是 `/api/health` 的 `history_available`**：健康检查在服务初始化期间是 **503**，
而**那时历史其实是好的**（历史刻意不被 `_require_ready()` 挡住，见上），
按 health 判断会让侧栏在那几十秒里谎报「未同步」。

⚠ 侧栏那行「未同步到数据库，历史只保存在本机浏览器」**不是装饰**：数据库连不上时
**问答链路完全不受影响**，界面上再无别的信号，用户会以为历史已经存进去了。

**已知局限（有意接受，不修）**：① 删除时若服务端恰好不可达，这一发静默失败，
下次启动并集合并后它会**重新出现**（并集合并只增不删，且「本地有、服务端没有」与
「本地删了、服务端还有」在数据上无法区分，要分开就得再引一个墓碑表）。② 不做多标签页 /
多浏览器并发协调，后写覆盖先写。

### 删除全部（清空历史，2026-09-21 加）

侧栏「历史对话」那行右侧多了一个「清空」按钮（**只在 `conversations.length > 0` 时渲染**），
点了**原地**变成确认卡片 —— 不引模态框（仓库里 `Modal` / `Dialog` / `window.confirm`
命中数为 0），也**不加 Esc 关闭**（仓库里 Esc 只服务于「⋯」浮层，那里没有取消按钮；
这里按钮齐了，再加一条键盘通路只会多一个状态源）。

```
Sidebar（确认卡片） → useChat.deleteAllConversations → lib/api.deleteAllConversationsRemote
                                                              ↓
                              DELETE /api/conversations → conv_store.delete_all_conversations
```

**三个已与用户确认的决定**（两处与单条删除**有意不同**，都写进注释了）：

| 问题 | 决定 |
| --- | --- |
| `feedback` 表那几行 | **留着**（与单条删除一致：`feedback` 无外键，分析数据不跟着会话走） |
| 确认方式 | **原地二次确认**，不引模态框 |
| 服务端不可达时 | **先删服务端，成功才清本地**（单条删除是乐观的：本地先消失，失败静默） |

⚠⚠ **最后一条是本节的核心**：`mergeServerList` **只增不删**，所以服务端那份没删掉的话，
下次启动整个列表会**原地复活** —— 用户以为清空了，刷新后又全回来了。单条删除可以乐观，
是因为它的代价只是「再删一次」；这里代价是**整份历史**。
⇒ `deleteAllConversationsRemote` **必须把失败抛出去**（与 fire-and-forget 的
`deleteConversationRemote` 刻意相反），侧栏 `runClear` 的 catch 把后端那句中文
**就地显示**在确认卡片上（列表、`hits`、`activeId` 一个都不动）+ 一个「重试」按钮。

**三个守卫，各自挡的是一件完全不同的事**（`useChat.ts`，别把它们当成「一个意思」）：

- **`bulkDeletingRef`** —— 冻住所有写服务端的路径。没有它，`stop()` 之后 `run()` 的
  `finally` 会换掉对话对象身份 → 同步 effect 把每条都标脏 → `flush` 重发 → 这些 PUT 与
  DELETE **并发**，谁先落库没有保证 —— 清空之后又被写回来，只有下次刷新才看得见。
  它同时是 `flush` 的**循环体**里的 `break` 条件（失败路径上队列里可能还冻着几条，
  由 `finally` 解冻后补发）。
- **`inflightFlushRef`** —— 在途那一发 PUT 的 promise。它是**唯一**可能在 DELETE 之后落库的
  写（在冻结之前就发出去了），所以清空的第一步就是 `await` 它。单飞保证最多一个，
  且自带 `CONV_TIMEOUT_MS` 超时 ⇒ 等待有界。
  ⚠ 为此 `flush` 从 `async` 改成了**返回 promise**：若在**调用点**写
  `inflightFlushRef.current = flush()`，早退路径返回的是一句**立刻 resolve** 的 promise，
  会覆盖掉真正在途的那一发，清空于是跳过等待直接发 DELETE。赋值必须在守卫**之后**。
- **`mergeGenRef`** —— 启动合并的代际。清空在**那次 `listConversations()` 发出之后**成功时，
  手上那份列表是「删除前」的世界，合并进去会在侧栏留下几条幽灵（点开 404、静默停在原地，
  只有刷新才自愈）。⚠ 只作废**列表合并**那一段，`setServerMode(true)` / `setHistorySynced(true)`
  照置 —— 它们证明的是「库是通的」，与这份快照新不新无关。
  ⚠ 别让单条 `deleteConversation` 去自增它：那会把整个启动合并白丢一次。

⚠⚠ **`setPendingJump(null)` 不是打扫卫生**（最容易漏、后果最怪）：`page.tsx` 的自动滚到底
写着 `if (jumpRef.current) return;`，而挂在**已删**对话上的 `pendingJump` 永远不会被那个
1.5 秒兜底清掉 —— 定位 effect 在 `pendingJump.conversationId !== activeId` 时**直接 return，
连计时器都不挂**。于是视口此后**永久**不再自动跟到最新，症状与搜索、与删除都看不出关系。

⚠ **`stop()` 放在请求成功之后、不放请求前**：决策是「本地一条不动」，在失败路径上 abort
掉用户正在看的回答是一次**本地破坏** —— 库连不上时他白白丢了一轮回答，却什么都没删成。

⚠ **`historySynced` 不动**：它说的是「历史**能不能存进**数据库」。删成功不代表存得了 ——
若 `serverMode === false`，把它翻成 `true` 会让琥珀提示消失，而之后新问的对话**照样存不进去**。

⚠ **`localStorage.removeItem` 是显式的**，不指望落盘 effect 写 `"[]"`：那条路依赖 `setItem`
成功，而超配额 / 隐私模式下它会抛、**旧值原样留着** → 下次启动本地那份复活 → 自愈扫描
整批 PUT 回服务端。

⚠ `DELETE /api/conversations`（**1 段**）与 `DELETE /api/conversations/{conv_id}`（**2 段**）
**不冲突**，谁先声明都一样 —— FastAPI 按路径**段数**匹配。上面「`search` 必须声明在
`{conv_id}` 之前」那条规矩只在**同方法 + 同段数**时成立，别看着像就照搬
（`probe_conv_store.py` ⑪ 拿「两条同时都还能打到」钉住）。这条路由**不做任何确认** ——
后端没有别的守卫可言（单用户、无鉴权、没有可问的对象），防误触的唯一落点是侧栏那个二次确认；
**curl 打这一发就是真删**。

⚠ 失败文案是**专用**的 `_DELETE_ALL_UNAVAILABLE_MSG`（「对话历史数据库暂时不可用，
未删除任何对话。」），**不复用默认那句** —— 那句说的是**保存**（「本次对话将只保存在本机
浏览器」），用户点的是**删除**，答的不是他问的问题。同 `_FEEDBACK_UNAVAILABLE_MSG` 的由来，
而侧栏会把这句话**原样显示**在按钮下面，更要说对。

**探针 ⑬ 的做法：在「必定回滚」的事务里跑真函数**（不是跳过，也不是快照-恢复）。

```python
with conn.transaction():
    ... 前置安全断言（真在事务里 + 与被测函数同一条连接）...
    deleted = conv_store.delete_all_conversations()
    ... 断言 ...
    raise _RollbackSignal          # ⚠ 必须是异常：正常退出会 COMMIT = 真删
```

⚠⚠ 用例**刻意不用 `[SKIP]`**：这台机器库里有用户的真实对话，「空库才跑」等于永远不跑。
机制是本仓库已验证过的（`save_conversation` 正在生产里依赖它）：psycopg 在
`autocommit=True` 的连接上，`with conn.transaction():` 在事务 IDLE 时**会发真 BEGIN**
（`conv_store.py` 里 `save_conversation` 那段注释记着源码依据）。进程被 kill 也安全 ——
连接一断，PG 自己回滚未提交的事务。实测跑完 `usage_stats()` 与两条真实对话（含正文）
逐条都在。

⚠⚠ **前置断言用 `raise _AbortCheck` 而不是探针里的 `check()`**：`check()` 只记一笔失败然后
**继续往下执行**，而在这里继续执行 = **在真实的库上做实验**。全仓库只有这一处需要这种语义。

⚠ 最值钱的一条断言是 `deleted == 删除前整表 count(*)`，它一次钉三件事：真删光了 /
**没有 WHERE 子集**（将来有人加 `user_id` 过滤时会当场变红）/ 条数不是猜的。

⚠ **`cleanup()` 上面有一条注释**：绝不能图快改用 `delete_all_conversations()` ——
那会把用户真实的历史对话一起删光。前缀过滤在这里不是「顺手加的一道」，
它就是「只删自己那几条」这件事本身。

## 用户反馈（`feedback` 表，2026-09-21 加）

每条回答可以点 👍/👎，存进 `feedback` 表。**本次只做「收集 + 可查」**（2026-09-21 与用户确认
的范围）：反馈**不回流**到检索或生成。理由：语料只有 74 条，按反馈调 doc 权重必然过拟合，
而「怎么调」本身需要另做标定。要拿它调策略，先设计标定方案。

⚠ 顺带一条：**`.env` / `config.py` / `.env.example` 一个字都没动** —— 反馈与对话历史
共用 `POSTGRES_HOST` 这一个开关、同一条约连接（同「对话历史与采购库共用开关」的先例），
所以绕开了本仓库记过四次的三处同步陷阱。

### ⚠⚠ 表上**一处外键都没有** —— 这是整个设计唯一的关键决定

直觉写法是 `message_id text REFERENCES messages(id) ON DELETE CASCADE`，**那是错的**，
而且错得完全看不见：

`conv_store.save_conversation()` 每次保存都
`DELETE FROM messages WHERE conversation_id = %s` 再整批重插（见该函数），而前端
**一轮回答就 PUT 一次**（`useChat.ts` 的同步边界）。于是外键的级联会在**下一次自动保存时
把这条对话上所有的 👍/👎 静默删光** —— 不报错、界面上完全看不出来，几周后翻库才会发现
反馈少了大半。

不加外键还顺带对了第二件事：**对话被删掉后反馈仍然留着**。`delete_conversation()` 靠级联
删消息，而「攒下来用于优化检索」要的正是这个（分析数据不该跟着会话走）。

⚠ **这条不能只靠注释守**：`scripts/probe_feedback.py` ⑦⑧ 两条**行为断言**钉着它
（重新 `save_conversation()` 后反馈行还在、`delete_conversation()` 后反馈行仍在），
⑦ 还额外查一次 `pg_constraint` 拿「库里确实没有外键」的独立凭证。
**谁日后「顺手把外键补上」，那两条会当场变红。**

⚠ ② 断言 `REFERENCES` 时**必须限定在 feedback 那一条 CREATE TABLE 语句里**，不能查整个
`_DDL` 拼接串 —— 那里面本来就有 `messages` 的 `REFERENCES conversations(id) ON DELETE
CASCADE`，整串检查会以一个**完全错误的理由**变红（写探针时先踩了一次，报出来像是
「刚写的无外键规则被自己违反了」）。② 里专门留了一条**范围凭证**断言把这件事记在案。

### 同一个事实存两处，**互不替代**

| | 存哪 | 用途 | 谁写 |
| --- | --- | --- | --- |
| **哪个拇指亮着** | `Message.feedback`（`1 \| -1`，undefined = 没评过） | 界面 | 前端随 `payload jsonb` 走，**后端零改动** |
| **这次评价是什么** | `feedback` 表（含 question / answer / doc_ids 快照） | 分析取数 | 前端点按钮时显式 PUT 一条 |

- 右边那半**不需要任何后端改动**：`ConversationUpsert.messages` 是 `list[dict[str, Any]]`，
  `messages` 表只从 jsonb 里生成 `role` / `content` 两列 —— 新字段原样进 `payload`、
  原样回来。刷新后拇指照样亮着。（探针 ⑦ 拿 `feedback=1` 的消息钉着这条。）
- 快照**由前端给**，后端不去 `payload` 里翻 —— 那等于让后端解释 `Message` 的内部结构，
  而 `schemas.py` 明写「原样进 payload，**不解释**它内部的结构」。
- ⚠ **POST 失败时两半会漂移**（拇指亮着但没入库）。**有意接受**：界面上不会因为一次网络
  抖动把用户刚点的 👍 自己弹回去，代价是少一行分析数据。所以 `useChat.setFeedback` 里
  那两个调用一律 `.catch(() => {})`、**本地先行**（照 `deleteConversation` 的成例）。
- ⚠ `answer` 快照是**评价那一刻**的正文。日后 `regenerate` 重出答案，旧反馈仍指向旧正文
  —— 这是对的，评价的就是那一条。

### 表结构与三个函数

```sql
feedback (conversation_id text, message_id text, rating smallint,
          question text DEFAULT '', answer text DEFAULT '',
          doc_ids jsonb DEFAULT '[]'::jsonb,
          created_at timestamptz, updated_at timestamptz,
          PRIMARY KEY (conversation_id, message_id))
+ CREATE INDEX feedback_created_idx ON feedback (created_at DESC)
```

- **主键 `(conversation_id, message_id)`** ⇒ 同一条消息再评一次是 **upsert**，靠
  `ON CONFLICT … DO UPDATE`；**`created_at` 保持首次那一个**（同 `conversations` 的约定），
  只有 `updated_at` 变。⑥ 钉着。
- ⚠ `doc_ids` 是 `jsonb` 而**不是 `text[]`**，且**必须包 `Jsonb(...)`** —— 裸 `list` 会
  `ProgrammingError: cannot adapt type`，类型检查发现不了，只有真跑一次才暴露
  （同 `save_conversation` 里那处）。
- ⚠ 时间戳照旧 `timestamptz` + `_to_ts` / `_to_ms`，**转换只在本模块内做**
  （`datetime` 不是 JSON 可序列化的，漏到路由层会在 `api.py` 的 `json.dumps` 处炸 ——
  本项目第五次）。
- `_guard(action, fn, msg=_UNAVAILABLE_MSG)` 与 `_run(sql, params, msg=…)` 都加了
  第三个**带默认值**的形参，现有调用点一个字不改。反馈传
  `_FEEDBACK_UNAVAILABLE_MSG = "反馈数据库暂时不可用，这次的评价没有保存。"`。
  ⚠ 复用对话历史那句的话，用户点了 👎 会读到「本次对话将只保存在本机浏览器」——
  说的是一件**没发生的事**（对话好好地存着，丢的是评价）。
  ⚠⚠ **`list_feedback` 走的是 `_run` 那条路**，一开始漏传 `msg`，`_guard` 就用默认值抛了
  那句关于**对话**的话 —— 是 `probe_feedback.py` ③ 那条「文案必须是反馈那句」的断言当场
  逮住的，**不是**靠读代码发现的。加新的查询函数时别漏。

三个公开函数照 `list_conversations` / `get_conversation` / `delete_conversation` 的形状：
`save_feedback` / `delete_feedback`（**幂等**：删不存在的 key 是空操作，对应「再点一次 =
取消」）/ `list_feedback(rating=0, conversation_id="", limit=100)`
（`rating=0` = **不过滤**，`limit` 按 `_FEEDBACK_HARD_CAP=500` 夹紧）。

⚠ `list_feedback` 的 WHERE 是**按有没有条件在代码里拼**的，但拼进去的只有
`"rating = %s"` 这种**字面量片段**，值一律走 `%s` —— 与「绝不把调用方给的字符串拼进
SQL 文本」（`pg_store` 那条铁律）不冲突。

### 三条路由（无 `_require_ready()`）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| PUT | `/api/feedback/{conversation_id}/{message_id}` | upsert。`rating ∉ {1,-1}` → **400**，**在碰 store 之前**就拒 |
| DELETE | `/api/feedback/{conversation_id}/{message_id}` | 取消评价，**幂等** |
| GET | `/api/feedback?rating=0&conversation_id=&limit=100` | `list[FeedbackRow]`，供分析取数 |

- ⚠ 与其他可选能力一样**不调 `_require_ready()`**：反馈不碰 Qdrant / 向量模型，挂在索引
  加载上只会让功能在重启后消失几十秒。④ 用 `TestClient` **不进 `with`** 顺带钉着这条。
- ⚠ `rating` 声明成 `int` 而**不是 `Literal[1, -1]`**：非法值要走路由里那句**中文** 400
  （「rating 只能是 1（👍）或 -1（👎）」），而不是 pydantic 的 422 英文报错 ——
  与「搜索词为空 → 400」同一条惯例。④ 里还断言了「400 时**没有**碰到 store」。
- ⚠ 限流自动生效、**每端点一个桶**，不用额外接线。
- `HealthResponse` **没动**：反馈与历史共用同一条连接、同一个 `history_*` 状态
  （`_bootstrap` 的 `conv_store.warmup()` 顺手就把表建了，**不需要新的 stage**）。

### 前端

- **`Message.feedback?: 1 | -1`**（`lib/types.ts`）—— 见上面「存两处」那张表。
- `lib/api.ts` 加 `putFeedback` / `deleteFeedback`（那节注释从「五个函数」改成**七个**）。
  两条都**不做 snake_case 转换**（请求体字段名前端后端一致），且是 **fire-and-forget**。
- ⚠⚠ **`patchMessage` 加了第四个形参 `bump = true`**，`setFeedback` 传 `false`。
  `updatedAt` 的语义是「对话**内容**什么时候变的」，而评价是关于内容的 metadata ——
  bump 了的话，给一条上周的旧对话点个 👍，下次刷新它会因为启动合并按 `updatedAt DESC`
  排序而**跳到侧栏最上面**（看起来像历史记录自己乱了）。
  ⚠ **不 bump 不影响同步**：脏判定是**对象身份**（`syncedRef`），每次都新构造了对象。
  现有调用点一个字没改。
- ⚠ `setFeedback` 有**三个守卫**：`conv.remote`（正文没拉下来，快照会存成空答案）、
  消息正在流式（评价的是哪一版说不清）、找不到对话/消息。与 `send` / PUT / localStorage
  那三处是同一批守卫。
- ⚠ 快照的 `question` 取**往前最近的一条用户消息**（中间可能隔着若干工具轮，但那都是这条
  回答的步骤、不是新提问），`doc_ids` 从 `msg.sources` 取（网页条目那条带 `web:` 前缀，
  与知识库条目天然分得开，不用额外标记）。
- **`ChatMessage` 的 `onFeedback` 是可选的**：不传就**不渲染**两个拇指
  （`page.tsx` 只在有活跃对话时传）。两个拇指**不受 `isLast` 限制** —— 每条答完的回答
  都该能评，不只是最后一条。
- ⚠ 动作行加了 **`flex-wrap gap-y-1`**：原先最多三格，加两个拇指后在 375px 上挤不下，
  不换行会被父列的 `min-w-0` **裁掉**（按钮还在、只是看不见，很难发现）。
- ⚠ `ActionButton` 的 `active` 态要**把 hover 一并覆盖掉**（`hover:bg-brand-soft
  hover:text-brand`）：只写 `bg-brand-soft` 的话，鼠标一移上去就被 `hover:bg-hover`
  盖回灰底 —— 选中的那个反而变暗。

### 已知局限（有意接受，别当成 bug）

1. **反馈不回流**：本次只收集（见本节开头）。
2. **POST 失败会静默丢一行**（界面照常）—— 见「存两处」那条。
3. **`answer` 快照是评价那一刻的正文**（`regenerate` 后旧反馈仍指向旧正文，这是对的）。
4. **带图提问的快照不含图片信息**（`question` 只有用户敲的字）—— 与分析目的无关，不做。
5. **无用户维度**：与对话历史同一条「单用户共享」假设，谁打开都看到同一份。
6. **👎 不带原因选择器**（用户 2026-09-21 明确要「就两个按钮」），表里只有 `rating`。
   要加原因得**手工 `DROP` + `CREATE`**（`CREATE TABLE IF NOT EXISTS` 对已存在的表是空操作、
   既不补列也不改列）。
