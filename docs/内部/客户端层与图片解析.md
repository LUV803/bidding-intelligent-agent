## 客户端层（`clients/`）

文本大模型与视觉模型原先各自焊死在一个模块里（`llm.py` 里只有 `DeepSeekLLM`，配置写死读
`settings.deepseek_*`），换一家文本供应商要改生产代码。2026-09-20 抽出 `clients/` 包：

```
clients/base_client.py     BaseLLMClient（契约）+ OpenAICompatLLM（共享实现）
                           + ToolCall / LLMEvent / _MarkupSuppressor / strip_tool_markup
clients/llm_factory.py     get_llm()：按名字选供应商，**每家一个缓存实例**
clients/deepseek_client.py DeepSeekLLM（默认）
clients/zai_client.py      ZaiLLM —— 智谱 GLM-4.7-FlashX，纯文本
clients/vision_client.py   智谱 glm-4.6v-flashx（图片解析，**同步**，不属于 LLM 契约）
```

⚠ **`llm.py` / `vision.py` 现在只是转发 shim**（用户要求保留老路径），新代码一律
`from .clients import ...`。两处细节：① shim 里下划线开头的名字**必须显式再导出**
（`import *` 会跳过下划线名，而 `probe_markup.py` 用的是 `_MarkupSuppressor` 那套）；
② **`vision.py` 刻意不转发 `_client`** —— 模块全局经转发模块赋值会**静默变成空操作**
（真模块的 `_get_client()` 读的是它自己的全局），`probe_vision.py:254` 因此改成
`from bidding_qa.clients import vision_client as vision`。**实例**属性（`llm._client`）
不受影响，照旧转发。

### ⚠ 两家文本客户端**不是两套 HTTP 实现**

DeepSeek 走 `openai` SDK 的 `AsyncOpenAI`（只有 `chat.completions`），而 **GLM-4.7-FlashX
也是 OpenAI 协议兼容**。所以硬写两套 HTTP 只会把 200 行流式拼装逻辑抄两遍 —— 真实形状是
**一个 `OpenAICompatLLM` 共享实现 + 两份配置映射**，`DeepSeekLLM` / `ZaiLLM` 各自只做一件事：
从 `settings` 读自己那份配置。`stream()` / `stream_with_tools()` / `complete()` 的**契约
一个字没动**（`probe_web_search.py` ⑫ 用替身逐事件钉着），`_MarkupSuppressor` 也搬进 base
供两家共用。

⚠ `temperature` / `max_tokens` 的默认值从**直接读 `settings.deepseek_*`** 改成了
`default_temperature` / `default_max_tokens` 两个抽象属性。**加新供应商时必须实现它们**，
漏了就是静默拿 DeepSeek 的默认值（在 GLM 上不会报错，只是行为不对）。

### ⚠⚠ `BaseLLMClient` 是**只做契约声明**的抽象基类，别加运行期关卡

这是本仓库**第一个** ABC（此前 `Protocol` / `ABC` / `abstractmethod` 命中数为 0）。
它的**唯一消费方是类型标注** —— `eval_rag.py` / `probe_recover_e2e.py` / `probe_web_search.py`
的假 LLM 全是鸭子类型，**不继承它**。在基类上加 `isinstance` 校验会把那些替身挡在门外，
探针集体报假失败。同理 `vision_client` **不继承 `BaseLLMClient`**：它是同步的、
`analyze() → VisionResult`、走 `zai-sdk`，与 `stream` 契约没有共同接口，硬塞进去只会
造出一个每次都要 `raise NotImplementedError` 的假抽象（同「图片解析」一节那条判断）。

### `LLM_PROVIDER` 切换供应商

`LLM_PROVIDER=deepseek`（默认）| `zai`。⚠ **环境变量优先于 `.env`**，所以切换着测不用改文件：

```bash
LLM_PROVIDER=zai uv run python scripts/probe_tools.py
LLM_PROVIDER=deepseek uv run python scripts/probe_tools.py   # 对照
```

⚠ **新增配置项要三处一起改**（`config.py` / `.env` / `.env.example`，`extra="ignore"`
那个记过四次的坑）—— 本次加的是 `LLM_PROVIDER` + `zhipu_chat_model` /
`zhipu_chat_temperature` / `zhipu_chat_max_tokens`。
⚠ 配置项**沿用 `zhipu_` 前缀而不是新建 `zai_`**：`.env` 里用户已经填了 `ZHIPU_API_KEY`，
新建前缀会让老 `.env` 的键被静默丢弃。模块名叫 `zai_client.py` 只是因为 SDK 叫 `zai`。
⚠ 工厂**遇未知值退回 deepseek + 记 WARNING，不抛**（同 `QDRANT_MODE=auto` 的惯例）：
`LLM_PROVIDER=zaip` 这种拼错若抛异常，服务直接起不来。

⚠ **`LLM_PROVIDER` 现在只是「默认值」，不再是唯一开关**（2026-09-21 起，见下一节）。

### ⚠⚠ 按请求切换供应商（2026-09-21 加，前端那个胶囊）

**第二个「每请求可变」的维度**（第一个是 `web_search`，见「联网搜索」）：

| | 进程级 | 请求级 |
| --- | --- | --- |
| 文本供应商 | `settings.llm_provider`（`.env` 的 `LLM_PROVIDER`）—— 现在只是**默认** | `ChatRequest.llm_provider`（前端工具条上那个循环胶囊） |
| 联网搜索 | `web_search.ENABLED`（有没有 Key） | `ChatRequest.web_search`（用户这次开没开） |

**与联网那对的关键差别**：联网是两个维度**取交集**（没 Key 时开关打开也不搜）；供应商是
**一维覆盖**——名字认得出来就照办，**没配 Key 就如实报没配，绝不悄悄换成另一家**。
静默换模型 = 用户拿到一个他没要的模型的答案，比报错糟得多。

```python
_PROVIDERS = {"deepseek": DeepSeekLLM, "zai": ZaiLLM}
_LABELS    = {"deepseek": "DeepSeek",  "zai": "GLM"}   # 胶囊上显示的字
_llms: dict[str, BaseLLMClient] = {}                   # 原先的模块级单例 _llm

resolve_provider(name)      # 归一化 + 未知值降级（搬现有那段 WARNING）
get_llm(provider=None)      # 形参可选 ⇒ 全仓 16 处无参调用点一字不改
available_providers()       # [{name,label,model}]，**只列 ready 的**
```

- **按名缓存**，不是每次 `cls()` 新建 —— 缓存住实例也就缓存住了它懒建的 `_client`
  （`base_client.py` 的 `client` property），**连接池不丢**。`probe_llm_provider.py` ②
  拿一个 `sentinel` 塞进 `_client` 再取一次，钉的就是这件事。
- ⚠ **归一化只在 `resolve_provider` 里做一处**。`api.py` 的两处调用点是
  `get_llm(payload.llm_provider or None)` —— **空串 → `None` → 默认**，这个名字**照传不归一化**
  （大小写/空格在 `get_llm` 里处理）。两处都归一化就会有两套口径。
- ⚠ 未知名字也**照传**，降级发生在 `resolve_provider` 里 —— handler 不预先过滤，
  否则「未知值降级」那条就没有真机路径了。
- **`available_providers()` 只列真配了 Key 的**：名字合法但没配 Key 的点了必然失败，
  摆出来是骗人。前端因此**只在 ≥2 家时才渲染**那个胶囊（只有一家时没有可选项）。
  ⚠ 这条是**读活的 `settings`**，不是 import 期的快照 —— 真机验过：把一个进程的
  `ZHIPU_API_KEY` 抹空，`/api/health` 的 `llm_providers` 当场只剩 DeepSeek 一家。

**加第三家供应商要做的事**（漏一条的表现都写在括号里）：

1. `clients/` 写一个 `BaseLLMClient` 子类 → `_PROVIDERS` 加一条 →
   `_LABELS` 加一条（**漏了胶囊显示成键名**，`probe_llm_provider.py` ③ 挡着）
2. ⚠⚠ **必须写自己的 `_NOT_CONFIGURED`**（`base_client.py` 有默认的那句）。
   `rag._no_key_hint()` 是**从 `llm._NOT_CONFIGURED` 里切出键名**的 ——
   漏写会退成中性话「未配置 API Key，」，不指错但也不具体。
3. `probe_llm_provider.py` ③ 的 `_KEY_FIELD` 映射加一行（**漏了那条「抹掉 Key 后它必须
   从列表消失」的断言会静默跳过**，而它是「只列 ready 的」唯一的真凭证）

⚠⚠ **`rag._no_key_hint()` 与真机撞到的一个 bug**（2026-09-21 修）：降级提示原先**写死**
`未配置 DEEPSEEK_API_KEY`，而每请求供应商一加，选了 GLM 的用户会被指去查一个
**本来就配好了**的键。修法是 `fallback_answer(sources, llm_ready, llm=None)` 多收一个客户端、
从它的 `_NOT_CONFIGURED` 里点名。⚠ **不传 `llm` 时给中性的「未配置 API Key，」而不是
继续默认成 DeepSeek** —— 那正是本仓库记过的 `default_temperature` / `default_max_tokens`
那个坑（「漏了就是静默拿 DeepSeek 的默认值」）。DeepSeek 那一路的**逐字节原文**由
`probe_llm_provider.py` ⑥ 单独钉一份（`probe_web_search.py` ⑥ 那条两参调用已改成中性话）。

**两条已知局限**（都在 `probe_llm_provider.py` 的注释里，别当成 bug）：

- **`/api/health` 只能报默认那家** —— 它没有请求上下文。与 `web_configured` vs
  `ChatRequest.web_search` 是同一条限制（`api.py` 里有先例注释）。所以 health 的
  `llm_provider` / `llm_model` / `llm_ready` 描述的是**服务端默认**，不是「这次用的」。
- **切换只影响之后的提问**：已有消息仍是旧模型产出的，界面上不标注是哪家答的。
  历史只回传 `{role, content}`（不带任何供应商痕迹），所以**一个对话里混用两家是安全的** ——
  我最初以为会撞上跨供应商的 `reasoning_content` 400，**核实后不成立**：带 `tool_calls` 的
  assistant 消息只存在于**单次请求内部**的工具循环里，从不落库、从不回传。

改 `clients/llm_factory.py` / `schemas.py` 的 `ChatRequest`·`HealthResponse` / `api.py` 里
那两处 `get_llm(...)` 之后跑：

```bash
uv run python scripts/probe_llm_provider.py   # 64 条，**全离线**（不需要任何 Key / 服务 / 网络）
```

### GLM 走 Agent 链路的实测结论（2026-09-20）

**功能上完全可用**：工具调用拼装、多轮、`finish_reason='stop'` 带正文、
`{"thinking":{"type":"disabled"}}` **确实生效**（强制轮 `reasoning_seen=False`）。
但**两条 DeepSeek 服务端特有的约束在 GLM 上不存在**：

| 约束 | DeepSeek | GLM-4.7-FlashX |
| --- | --- | --- |
| 具名 `tool_choice` + 思考 → 400 | ✅ 有 | ❌ 没有（不关思考也能具名强制） |
| 带 `tool_calls` 的 assistant 消息缺 `reasoning_content` + 下一轮开思考 → 400 | ✅ 有 | ❌ 没有 |

⇒ `probe_tools.py` 的 ⑤ / ⑤b 两条断言**按实际供应商分叉**（判据是
`type(llm).__name__`，不是 `settings.llm_provider` —— 工厂拼错时会静默回退，
以实际用的为准）。非 DeepSeek 时打 `[SKIP]`，**不是 FAIL** —— 不分叉的话
「换个 `LLM_PROVIDER` 再跑一遍探针」这条验证步骤会稳定给出两条假 FAIL，把真问题淹掉。
⚠ 但 `_assistant_tool_message()` **仍然无条件回传该字段**：那是为**跨供应商统一**，
多回传一个服务端不认的字段不会被拒，少回传则换个供应商就 400。别因为 GLM 不要求就删。

## 图片解析（`clients/vision_client.py`）

提问窗口的回形针把图片交上来，`POST /api/vision` 调智谱 `glm-4.6v-flashx` 抽成结构化字段
（项目名称/编号/采购人/金额/日期/标的物/关键条款 + 全文 + 摘要），前端渲染成「图片解析」卡片，
并把解析结果作为上下文附到这次提问上。

⚠⚠ **它不是 Agent 工具**（最容易改错的一点）。解析发生在上传那一刻，早于提问，也不由模型
决定要不要调 —— 与 `search_knowledge_graph` / `search_procurement_records` 是**不同形状**的东西。
做成工具会引入 `_match_schema` 投票、`_PARAM_ALIASES` 撞名、`recover_tool_calls` 归属等
一整套新风险，而需求里描述的本来就是「上传 → 解析 → 展示」。

**唯一的硬不变量：图片内容只进提示词，绝不进检索。**

```
/api/chat   retriever.search(question, ...)          ← 原问题
            stream_answer(llm, with_image_context(question, image_context), ...)

/api/agent  retriever.search(question, ...)          ← 原问题（agent.py 的预检索，一个字不改）
            build_agent_messages(with_image_context(question, image_context), ...)
            ↑ 工具内部的 retriever.search 同样是原问题
```

直觉上「把图片内容拼进 `question` 就完事」是错的：那样检索会拿着一整份招标公告去查——
向量被稀释、BM25 满屏乱命中，而 `MIN_VECTOR_SCORE=0.72` 是针对**当前语料**标定的，稀释后
极可能直接跌破阈值返回 0 条。结果就是「传图再追问」这条主打路径**比不开图片还差**。
`rag.with_image_context()` 的 docstring 里写清了这条，改它之前先读。

`image_context=""`（不传图）时 `with_image_context` **原样返回 `question` 本身**，
所以 `/api/chat` 的检索、提示词、SSE 事件序列与加这个功能之前**逐字节相同**。
`probe_vision.py` ① 有 4 条断言钉住这一点（`with_image_context(q, "") is q`）。

**几条实测结论与坑**：

- **base64 两种形态都能用，但边界上只让一种穿过**：`zai-sdk` 内部会调
  `drop_prefix_image_data()` 把 `data:image/...;base64,` 前缀**剥掉**再发（见
  `zai/core/_utils/_utils.py:402`），所以带不带前缀其实等价。约定是**前端切掉前缀、只发裸
  base64**；`/api/vision` 对带前缀的仍兼容，只记一条 WARNING。
- **`glm-4.6v-flashx` 是推理型模型**，思维链会先吃掉 `max_tokens`，给少了表现为
  「图传上去了，返回空」——最难查的那种。所以 `ZHIPU_VISION_MAX_TOKENS=4096`（不是 2048），
  且 `analyze()` 对空正文有**单独的错误分支**点明这件事。batch 那边踩过同一个坑。
- **模型不守 JSON 格式**：提示词里写了「不要 markdown 代码块」，实测两次调用**都**包了
  ```json 围栏。所以 `_extract_json()` 必须宽容（剥围栏 → 抠第一个 `{` 到最后一个 `}`），
  **解析失败就降级**：原文整段塞进 `full_text`、`ok=True` 照常返回，绝不报错。
- **`VisionResult.fields` 的值必须全是 `str`**：模型会把金额返回成数字、关键条款返回成数组，
  `_as_text()` 统一转换。理由与 `PgResult` 不能留 `Decimal`/`date` 相同——`api.py` 的
  `json.dumps` 会在那里炸。
- **有 `_HOISTED_FIELDS` 那三个**（文档类型/全文/摘要）：它们被提升成 `VisionResult` 的
  一级字段，`_to_fields()` 要把它们从 `fields` 里排掉，否则卡片上重复出现。
- **`vision.analyze()` 是同步函数**（SDK 只有 `httpx.Client`，没有 `AsyncZhipuAI`），
  接口层用 `await asyncio.to_thread(analyze, ...)` 包——与 retriever / graph_store 一致。
- **`/api/vision` 刻意不调 `_require_ready()`**：图片解析完全不碰 Qdrant/BM25，挂在索引
  加载上等于让独立能力被核心链路拖死。
- **也刻意不在 `_bootstrap()` 里预热**（图谱和采购库都预热了）：视觉能力没有任何冷连接成本，
  预热只会多一次网络往返、多花一次钱。**别「补全」它。**
- **`vision_status()` 只读模块变量，不发起任何网络调用**：`/api/health` 每 30 秒轮询一次，
  不可能每次真调一次视觉 API。所以 `vision_available` 读的是「配了 Key + 装了 SDK」以及
  **最近一次真实调用的成败**——刚起服务时偏乐观。前端因此**不按它给附件按钮置灰**。
- **图片不落盘、不进 localStorage**：只在内存里过一遍 base64。`Message.image` 存的是
  `VisionPayload`（解析结果），**原图 base64 用完即弃**——`useChat` 会把整个 conversations
  写进 localStorage（约 5MB 配额），塞进去是**静默**失败。
- **历史回传要补前缀**：`useChat.run()` 里给带 `image` 的历史消息套 `withImageContext()`，
  否则追问第二轮图片上下文就丢了（模型看不到上一轮问的是哪个项目）。模板在
  `frontend/lib/types.ts` 与 `rag.with_image_context()` 里**各有一份**，改一边要改另一边。

改 `clients/vision_client.py` 或提示词接线之后跑：

```bash
uv run python scripts/probe_vision.py   # ① 离线接线断言（含冻结路径不变量）② 真机试调
```
